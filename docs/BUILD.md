# Building Hermes Interactive UI+ (Android local, web, iOS / macOS on a Mac)

No `android/` or `ios/` folder is committed; they are generated by `expo prebuild` (CNG) inside a build copy.
Android APKs are built **locally on the build host** by `scripts/build-apk.sh` inside a memory-capped systemd scope.

## Flavors: official `hermes` build vs. `personal` build + private overlay
One repository, two build flavors, selected at build time with `FLAVOR` (all build scripts) =
`EXPO_PUBLIC_FLAVOR` (inlined into the JS bundle, read in one place: `app/src/flavor.ts`).

| | `FLAVOR=hermes` (default, official) | `FLAVOR=personal` |
|---|---|---|
| Name / ids | `Hermes Interactive UI+` (home-screen label `Hermes UI+`), `xyz.hermesui.app` (defined once in `app/brand/identity.json`, see "Identity") | from the overlay (`app/identity.json`) – must differ, so both apps install side by side |
| Deep-link scheme | `hermesuiplus://pair` | from the overlay (e.g. `hermesui://pair`) |
| Icons | official icon in `app/assets` + `app/public/icons` (from `app/brand/icon/*.svg`, `scripts/brand-icons.mjs`) | from the overlay |
| Web output | `dist/web/` | `dist/web-personal/` |
| APK | `dist/hermes-ui-plus-<variant>-<sha>.apk`, `dist/latest-hermes-<variant>.apk` | `dist/hermes-ui-<variant>-<sha>.apk`, `dist/latest-<variant>.apk` |
| Onboarding | QR / pair link or Hermes URL → done (+ demo) | + same-origin web app |
| Pair link of another kind | "not supported in this build" (`unsupported-in-build`) | accepted |
| Connections | Hermes (bridge / direct) + offline demo only | the same (own identity) |

Pair-link parsing accepts `hermesuiplus://`, `hermesui://` and the retired `hermesiui://` in both flavors (the scheme only
decides which app the system camera / browser opens). The UI bridge prints `hermesuiplus://` links; set
`BRIDGE_PAIR_SCHEME=hermesui` for a bridge that pairs a personal build.

`scripts/brand-icons.mjs`; mirrored (and checked by tests) in `app/src/brand.ts`, `bridge/src/pair.mjs` and
`scripts/make-pair-link.mjs`, which must run without the repo.

Icons: `node scripts/brand-icons.mjs [--concept <id>]` (round 1: monogram, bubble, stroke; round 2: courier, delivered,
dispatch, petasos, pointer, talaria) renders the chosen SVG concept into
`app/assets/*` (iOS 1024 opaque, Android adaptive foreground/background/monochrome, favicon), `app/public/icons/*`
(192/512, maskable, apple-touch) and `desktop/src-tauri/icons/*` (via `tauri icon` after `cd desktop && npm ci`), and
writes previews of all concepts to `dist/share/design/brand/index.html` (round 1) and
`dist/share/design/brand/round2/index.html` (`--previews-only` renders just the previews). It needs ImageMagick and
`@resvg/resvg-js` (`npm i --prefix /tmp/hui-brand-tools @resvg/resvg-js`; not a repo dependency).

### Private overlay (`HUI_PRIVATE_DIR`, default `~/work/hermesiui-private`, never inside the repo)
Everything personal lives outside the repository. Layout (all optional except `app/identity.json` for personal builds):
```
$HUI_PRIVATE_DIR/
  app/identity.json      personal name, slug, iosBundleId, androidPackage, scheme, icon paths (relative to app/);
                         optional desktopName / desktopId for scripts/build-desktop-{mac,linux}.sh
  app/assets/…           personal icons referenced by identity.json
  app/personal.env       EXPO_PUBLIC_* defaults of the personal build (e.g. EXPO_PUBLIC_PERSONA_NAMES) – no tokens
  build.env              build-machine settings for the scripts: MAC_HOST, LINUX_HOST, TEAM_ID, IOS_PUBLIC_BASE,
                         DESKTOP_PUBLIC_BASE
  web/<name>.env         branding of a personal web app: EXPO_PUBLIC_APP_NAME/_SHORT_NAME/_THEME_COLOR(_DARK), BRAND_ICON
  branding/…             images used by web/*.env
  pair-links.json        presets for scripts/make-pair-link.mjs --preset NAME (no tokens)
  .env.local             dev secrets (HERMES_BASE_URL, HERMES_API_KEY, BRIDGE_TOKEN, …): `cd bridge && node --env-file="$HUI_PRIVATE_DIR/.env.local" src/server.mjs`
  leak-denylist.txt      private terms for scripts/leak-guard.mjs / scripts/flavor-guard.mjs
  docs/ …                maintainer-only notes (deploy prompts, reviews with real hosts, research)
```
`scripts/lib/flavor.sh` (sourced by the build scripts) validates `FLAVOR`, exports `EXPO_PUBLIC_FLAVOR` and
`HUI_PRIVATE_DIR`, and for `personal` loads `app/personal.env` + `build.env` (values already in the environment win).
`app/app.config.ts` reads `app/identity.json` only for `personal`; it fails if the file is missing or reuses the
official ids. A public checkout without an overlay builds the official app with no extra setup.

### A hermes build fails if it would include anything private
`scripts/flavor-guard.mjs` runs automatically in every hermes build:
- `--env`: `EXPO_PUBLIC_FLAVOR=hermes` and no personal `EXPO_PUBLIC_*` value (dev profiles, persona names, keys …);
- `--tree <build copy>` (before bundling): no `.env*` file, no symlink into the overlay, no file whose content equals an
  overlay file (sha256; overlay files that are identical to tracked repo files, like the generic icons, don't count),
  and (APK) the resolved Expo config has the official ids/scheme and no overlay path;
- `--output <artifact>` (after bundling; web dir, unpacked APK/IPA): no overlay file content, no overlay path, no term
  from `$HUI_PRIVATE_DIR/leak-denylist.txt` (via `scripts/leak-guard.mjs`) and none of leak-guard's generic findings
  (tailnet hosts, CGNAT/private IPs, e-mail addresses; these run with or without a denylist, unscannable files fail,
  inline `leak-guard:allow` markers don't count in output). On failure the artifact is not copied to `dist/` (web) or
  is deleted (APK / IPA).
In addition, the hermes builders run the release gate below (`scripts/scan-artifact.sh`, incl. gitleaks) themselves
before promoting output: APK (final, re-signed file), web (staged copy, replaces `dist/web` only when clean) and desktop
(desktop sources before upload, unpacked app / AppImage / .deb + download dir staged before replacing `dist/share/desktop*`). Without a
private overlay the builders use `scan-artifact.sh --public` (generic + gitleaks); with one the denylist is mandatory.
`SKIP_WEB=1` desktop builds refuse a reused bundle whose `dist/web-desktop.build-info` is not the same flavor / `sw=0`.
APK builds also fail when the keep-alive service (local module `modules/stream-keepalive`) is missing from the APK
manifest/dex, unless `EXPO_PUBLIC_BG_SERVICE=0` removed it on purpose (then its presence fails the build).

```
scripts/build-web.sh                                     # official PWA -> dist/web
FLAVOR=personal scripts/build-web.sh                     # personal PWA -> dist/web-personal
FLAVOR=personal scripts/build-web.sh --brand "$HUI_PRIVATE_DIR/web/<name>.env"   # branded PWA (own name and icon)
scripts/build-apk.sh release                             # official APK
FLAVOR=personal scripts/build-apk.sh release             # personal APK (side by side)
FLAVOR=personal scripts/install-apk.sh                   # installs dist/latest-release.apk
FLAVOR=personal node scripts/make-pair-link.mjs --preset <name> --token <TOKEN>
```


## Why hard limits
The scripts are written for a Linux build machine without swap that also runs other work. An unbounded Gradle + Kotlin daemon + Metro + up to 10 parallel clang processes can exceed 12 GB easily and take such a machine down, so everything heavy runs under these limits:

| Limit | Value | Purpose |
|---|---|---|
| `systemd-run --user --scope` `MemoryMax=8G`, `MemorySwapMax=0` | whole build tree | hard cap; the kernel OOM-kills only the build scope, never the desktop/agents |
| `MemoryHigh=7G` | soft cap | throttles/reclaims before the hard kill |
| `CPUQuota=600%` | 6 of 10 cores | leave 4 cores for interactive work |
| `org.gradle.workers.max=2` + `--max-workers=2` | | fewer parallel tasks/native compiles |
| `org.gradle.jvmargs=-Xmx3g -XX:MaxMetaspaceSize=768m`, `kotlin.daemon.jvmargs=-Xmx1g` | | bound JVM heaps |
| `NODE_OPTIONS=--max-old-space-size=2048` | | bound Metro/expo CLI |
| ninja wrapper `-j3` | | AGP starts ninja with all cores otherwise (see below) |
| `--no-daemon` + `./gradlew --stop` (EXIT trap) + scope stop | | no daemons left behind, also on failure |
| `ABIS=arm64-v8a` only | | phone is arm64; halves native compile memory/time |
| `flock ~/builds/.hermes-build.lock` | | only one build at a time |
| pre-flight: refuse if `MemAvailable < 10 GB` | | do not start on an already loaded box |

Rules: no emulator and no second build while a build runs. The script samples scope memory every 15 s into the log
(`[mem] scope=… peak=… hostAvail=…`) and prints the peak at the end. Exit code 137 means the scope was OOM-killed:
lower `GRADLE_WORKERS`/`GRADLE_XMX` and retry.

The ninja wrapper: the script renames `~/android/sdk/cmake/3.22.1/bin/ninja` to `ninja.real` and installs a
2-line shell wrapper adding `-j $NINJA_JOBS` (default 3). It is re-applied automatically if sdkmanager overwrites it.

## Toolchain (user-space, no sudo), all under `~/android`
- `~/android/jdk-17` — Eclipse Temurin 17 (React Native docs recommend JDK 17; higher versions may cause problems).
  The old build host's JDK 21 also worked, but 17 is the documented one.
- `~/android/sdk` — cmdline-tools (latest), platform-tools, `platforms;android-36`, `build-tools;36.0.0`,
  `ndk;27.1.12297006`, `cmake;3.22.1`; licenses accepted.
- Node >= 22.13 from the system (`node -v` = 22.x). Gradle 9.3.1 is fetched by the wrapper into `~/.gradle`.
- Downloads were kept in `~/android/dl` (JDK tarball SHA-256 checked against the Adoptium API, cmdline-tools zip
  against the checksum on developer.android.com). It can be deleted (~360 MB).

Re-install SDK packages if ever needed:
`JAVA_HOME=~/android/jdk-17 ~/android/sdk/cmdline-tools/latest/bin/sdkmanager --sdk_root=$HOME/android/sdk "platform-tools" "platforms;android-36" "build-tools;36.0.0" "ndk;27.1.12297006" "cmake;3.22.1"`

## Build
```
HERMES_KEYSTORE=… HERMES_KEYSTORE_PASS=… scripts/build-apk.sh release   # -> dist/hermes-ui-plus-release-<sha>.apk (+ dist/latest-hermes-release.apk), JS bundle embedded
ALLOW_DEBUG_SIGNED=1 scripts/build-apk.sh release   # local test without the release key -> dist/hermes-ui-plus-release-<sha>-debugsigned.apk
scripts/build-apk.sh debug      # -> dist/hermes-ui-plus-debug-<sha>.apk   (loads JS from Metro at runtime)
FLAVOR=personal scripts/build-apk.sh release   # -> dist/hermes-ui-release-<sha>.apk (+ dist/latest-release.apk)
```
Steps: pre-flight, lock, `rsync app/` -> `~/builds/hermes-ui-hermes/app` (personal: `~/builds/hermes-ui/app`; excl.
node_modules, .expo, android, ios, refs, `.env*`), then inside the scope: `npm ci`, flavor guard (hermes),
`npx expo prebuild --platform android --clean`, patch the generated
`android/gradle.properties` with the limits above, `./gradlew assemble<Variant> --no-daemon`. Log:
`dist/build-<variant>-<timestamp>.log`. `SKIP_NPM_CI=1` reuses node_modules if `package-lock.json` is unchanged.
Overrides: `MEM_MAX`, `MEM_HIGH`, `CPU_QUOTA`, `GRADLE_WORKERS`, `GRADLE_XMX`, `NINJA_JOBS`, `ABIS`, `BUILD_DIR`
(see script header). Raising them is at your own risk.
`ABIS=x86_64 scripts/build-apk.sh release` builds for the local emulator; non-default ABIs get a suffix
(`dist/hermes-ui-plus-<variant>-<sha>-x86_64.apk`, `dist/latest-hermes-<variant>-x86_64.apk`) so the phone APK is never overwritten.
(The arm64 APK does not start on the x86_64 emulator despite ARM translation: SoLoader looks for `lib/x86_64`.)

## Release signing
The Expo template signs release builds with the per-machine **debug keystore** (the script asserts it), and
`scripts/build-apk.sh` re-signs the final APK with `apksigner` when `HERMES_KEYSTORE` is set. Every published APK must
carry the same release certificate: Android and Obtainium refuse updates signed with another key, and README.md
publishes the certificate's SHA-256 fingerprint. Therefore (`scripts/lib/signing.sh`):

- `FLAVOR=hermes … release` **refuses to start** without `HERMES_KEYSTORE` (+ `HERMES_KEYSTORE_PASS`,
  `HERMES_KEY_ALIAS` default `hermes`).
- `ALLOW_DEBUG_SIGNED=1` is the explicit opt-out for local test builds. The output is named
  `dist/hermes-ui-plus-release-<sha>-debugsigned.apk` (link `dist/latest-hermes-release-debugsigned.apk`), so it can
  never be mistaken for a publishable APK.
- `HERMES_CERT_SHA256` (hex, colons optional; from the environment or `$HUI_PRIVATE_DIR/build.env`) pins the expected
  fingerprint. When it is set, a release APK whose final signer differs is deleted and the build fails. Without it the
  fingerprint is printed with a warning.
- Debug builds and the personal flavor are unaffected.

```
HERMES_KEYSTORE=<path>/release.jks HERMES_KEYSTORE_PASS=… HERMES_CERT_SHA256=<fingerprint> scripts/build-apk.sh release
```

Creating a key (once): `keytool -genkeypair -v -keystore <path>/release.jks -alias hermes -keyalg RSA -keysize 4096
-validity 10000`. Keep it outside the repository (`*.jks`/`*.keystore` are excluded from the build copy and must never
be committed) and back it up offline together with its password: losing it strands every installed copy.
The password is passed to `apksigner` as `env:HERMES_KEYSTORE_PASS`, never on the command line.
Switching keys requires uninstalling the app once on each device (signature mismatch).
The full release procedure (export, build, checksums, upload, npm) is in [RELEASING.md](RELEASING.md).

## Release gate: scan every artifact before it leaves the machine
Run this on **every** artifact you publish or hand to someone (details: `docs/LEAK-GUARD.md`). It unpacks an APK/AAB/IPA/zip
(or takes a directory such as `dist/web` or an unzipped `.app`) and runs `scripts/leak-guard.mjs --path` (private denylist
from `$HUI_PRIVATE_DIR` is **required** here, plus the generic patterns) and `gitleaks dir`. Non-zero exit = do not publish.
```
export HUI_PRIVATE_DIR=~/work/hermesiui-private
scripts/scan-artifact.sh dist/latest-release.apk     # Android
scripts/scan-artifact.sh dist/web                    # PWA (after scripts/build-web.sh)
scripts/scan-artifact.sh path/to/Hermes.app          # macOS desktop / iOS simulator build
scripts/scan-artifact.sh path/to/unpacked-appimage    # Linux desktop (unsquashfs / dpkg-deb -x first)
scripts/scan-artifact.sh path/to/app.ipa             # iOS
```
Release checklist: build -> `scripts/check.sh all` -> `scripts/scan-artifact.sh <artifact>` -> only then upload/share.

## Install on the phone (Android, Tailscale name `<phone>`)
- Script: `scripts/install-apk.sh` runs `adb install -r` of `dist/latest-hermes-release.apk` (`FLAVOR=personal`:
  `dist/latest-release.apk`; adb from `~/android/sdk/platform-tools`).
- Wireless adb over Tailscale (one-time pairing, phone must be online in Tailscale):
  1. Phone: Settings > Developer options > Wireless debugging > on > "Pair device with pairing code".
  2. `adb pair <phone>:<PAIR_PORT>` and enter the 6-digit code.
  3. `adb connect <phone>:<CONNECT_PORT>` (port from the main Wireless debugging screen; changes after reboots/toggling).
     Use the phone's `100.x` Tailscale IP if MagicDNS does not resolve.
  4. `scripts/install-apk.sh` (or `scripts/install-apk.sh -c <phone>:<CONNECT_PORT>`).
- Sideload without adb: copy the APK to the phone (Tailscale file share/Taildrop, `scp`, or
  `python3 -m http.server` in `dist/` and open `http://<build-host-tailscale-ip>:8000/…apk` in the phone browser),
  tap it and allow "Install unknown apps" for that app.
- Debug APK needs Metro (`npx expo start` in `app/`, port 8081 reachable over Tailscale; cleartext is enabled).
  The release APK is standalone.

## Permissions
Declared via config plugins in `app/app.json` (texts are German and neutral). Native changes need a new build (`expo prebuild`).
- Android: `CAMERA` (expo-camera, expo-image-picker), `RECORD_AUDIO` + `MODIFY_AUDIO_SETTINGS` (expo-audio, dictation),
  `READ_CALENDAR`/`WRITE_CALENDAR` (expo-calendar), `POST_NOTIFICATIONS` (+ `RECEIVE_BOOT_COMPLETED`, expo-notifications).
  Background audio/recording is disabled. The ONE foreground service is the local Expo module
  `app/modules/stream-keepalive` (autolinked from `app/modules/`, no config plugin: its own AndroidManifest merges
  `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `WAKE_LOCK` and the `dataSync` service). It runs only while a chat
  answer streams (setting "Finish answers in the background", default on) – see "Background turns" below.
- `SCHEDULE_EXACT_ALARM` is deliberately NOT requested (denied by default on Android 14+, needs a special-access grant). Timers and
  reminders are inexact in Doze (may be a few minutes late); in-app pills stay exact. Add it to `android.permissions` if exact alarms matter.
- `expo-image-picker` must not use `microphonePermission: false`: that strips `RECORD_AUDIO` from the whole manifest.
- iOS: camera, photo library, microphone and calendar usage strings; Reminders access is off. Deep link `hermesuiplus://pair` uses `scheme: hermesuiplus`
  (personal: the overlay's scheme, e.g. `hermesui`)
  (expo-router/Expo add the Android intent filter and iOS URL type).

## Background turns (long answers while the app is in the background)
- A running turn belongs to its conversation, not to the screen: the chat shell keeps the session of a chat with a running
  turn mounted (hidden) when the user switches chats / opens the drawer or settings (`src/background/turnRegistry.ts`,
  max. 3 hidden turns; a 4th stops the oldest, its partial answer is kept as "Stopped").
- Android: foreground service type `dataSync` ("fetch data / transfer data between device and cloud", developer.android.com
  fgs/service-types), started when a turn starts (the app is visible then: Android 12+ forbids starting a foreground service
  from the background) and stopped on finish / error / stop; notification "<Profil> antwortet …" with a "Stopp" action (Android
  shows it only after ~10 s). Android 15 limits dataSync to 6 h per 24 h (`onTimeout` → the service stops itself). Never
  sticky. A headless JS task runs alongside: React Native pauses JS timers in the background otherwise. All backends use it
  (Hermes too: it saves the bridge recovery round trip). Google Play: the `dataSync` type must be declared in the Play Console
  (FGS declaration with a short video); sideloaded APKs are not affected.
- Battery: after a cut answer the app shows a one-time hint that opens the app's system settings (`Linking.openSettings`) –
  no `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (Play only allows the direct request for apps whose core function breaks under Doze).
- iOS: no Expo API grants extra execution time (`expo-background-task` = BGTaskScheduler, scheduled by the system), so an
  answer survives only the seconds iOS allows after leaving the app. A cut answer of a direct backend (no server-side run)
  shows "The app was in the background …" with "Continue" (re-sends history + the partial answer with a
  hidden continue instruction) and "Start over".
- "Answer ready" (setting "Notify when an answer is ready", default on): local notification when the app is
  in the background (push preview setting respected), banner with "Open" + drawer dot in another chat/screen, "New
  answer ↓" pill when scrolled away. No FCM needed: the notification comes from the running app process.

## macOS desktop (Apple Silicon)
`[FLAVOR=…] scripts/build-desktop-mac.sh` builds the Tauri app (`desktop/`) for **aarch64-apple-darwin** (macOS 13+) on a Mac
over ssh (`MAC_HOST`, env or `$HUI_PRIVATE_DIR/build.env`): web bundle here (`WEB_SW=0`, `WEB_OUT=dist/web-desktop`),
`tauri build --bundles app,dmg` on the Mac, then a `.dmg`, a zipped `.app` and a download page in `dist/share/desktop*`.
`SKIP_WEB=1` reuses the bundle, `KEEP_CACHE=1` keeps the Rust target dir for fast rebuilds, `INSTALL=1` also installs into
`~/Applications` on the Mac.

**Signing:** with a Developer ID Application certificate (`MAC_P12`, `MAC_P12_PASS`) the app is signed with the hardened
runtime; with an App Store Connect API key (`ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_PATH`) the app and the `.dmg` are
notarized and stapled, so a download starts without a Gatekeeper warning. The secrets come from the environment (or the
private `.env.local`), live in a temporary keychain on the Mac for the run only and are deleted afterwards. Without them,
or with `MAC_SIGN=0`, the build is ad-hoc signed and not notarized (first launch needs *Open Anyway*). The release gate
(`scripts/scan-artifact.sh`) accepts the code signature of a signed `.dmg`. What the app does and how to check it on a Mac:
`desktop/README.md`.

## Linux desktop (AppImage / .deb, alpha)
`[FLAVOR=…] scripts/build-desktop-linux.sh` builds the Tauri app (`desktop/`, same shell as macOS) for **x86_64 Linux**
on a Linux build host over ssh (`LINUX_HOST`, env or `$HUI_PRIVATE_DIR/build.env`; may be the build machine itself
via an ssh alias). Same flow as `scripts/build-desktop-mac.sh`: web bundle here (`scripts/build-web.sh`, `WEB_SW=0`,
`WEB_OUT=dist/web-desktop-linux`; waits while another web build holds its lock) → rsync `desktop/` + bundle →
`npx tauri build --bundles appimage,deb` on the host, memory-capped (`MEM_MAX` 8G, no swap) with `CARGO_BUILD_JOBS=6`
(`JOBS`); it waits while an Android emulator (`qemu-system*`) runs there. npm cache, Tauri's linuxdeploy download and
TMPDIR live in the remote build dir, which is removed after the build (`KEEP_CACHE=1` keeps it for fast rebuilds;
`~/.cargo/registry` stays); `RUSTFLAGS` remap build paths out of the binary. The hermes release gate scans the unpacked
AppImage without the bundled third-party shared libraries, Debian copyright files and GSettings schema sources
(upstream authors' e-mail addresses), plus the whole .deb.

**Minimum distribution = glibc of the build.** A binary (and the libraries linuxdeploy bundles into the AppImage)
needs the glibc it was built against, so building on a current distro (Ubuntu 26.04: glibc 2.43) yields an app that only
runs on equally new systems. Therefore the build runs by default **in a container on an old base image**
(`LINUX_BUILD_IMAGE`, default `auto` = `ubuntu:22.04` when `docker info` works for the ssh user, else the host build):
`scripts/docker/desktop-linux-build.Dockerfile` (apt: WebKitGTK 4.1 / librsvg / appindicator dev packages,
build-essential, node 22.x, Rust pinned to `RUST_VERSION`, override `LINUX_RUST_VERSION`) is built once on the host as
`hermes-desktop-build:<base>-<Dockerfile hash>` and reused (`LINUX_IMAGE_REFRESH=1` rebuilds it with current apt
packages / Node). The container runs as the unprivileged ssh user's uid, `--cap-drop ALL`, with only the build dir and
the cargo download cache mounted and `--memory $MEM_MAX --memory-swap $MEM_MAX`. Result on Ubuntu 22.04: the binary
needs glibc >= 2.34 (it was 2.39 when built on the host), everything inside the AppImage <= 2.35, so Ubuntu 22.04+ /
Debian 12+ are supported. `build.txt` records the toolchain image and the glibc requirement (`objdump -T`).
`LINUX_BUILD_IMAGE=host` builds directly on the host in a `systemd-run --user --scope` (needs the toolchain below;
the host's glibc becomes the minimum). Docker access is a root-equivalent privilege of the docker group (rootful
daemon): the script only uses it for this unprivileged container; with a rootless runtime the same flow applies.

Requirements on the host (no sudo needed once installed): container mode: docker usable by the ssh user, `dpkg-deb`,
`objdump`; host mode: rustup/cargo in `~/.cargo`, node + npm, `libwebkit2gtk-4.1-dev`, `librsvg2-dev`,
`libayatana-appindicator3-dev`, `build-essential`, `file`, `systemd-run`. On the build machine: `unsquashfs`, `dpkg-deb`
(release gate). Output:

| flavor | published to | files |
| --- | --- | --- |
| hermes | `dist/share/desktop-linux-plus/` | `hermes-ui-plus_<ver>_x86_64.AppImage`, `hermes-ui-plus_<ver>_amd64.deb` |
| personal | `dist/share/desktop-linux/` | `hermes_<ver>_x86_64.AppImage`, `hermes_<ver>_amd64.deb` |

plus `index.html` (download page), `icon-256.png`, `build.txt`; log in `dist/build-desktop-linux-<timestamp>.log`. A
hermes build is promoted only after flavor-guard + release gate on the unpacked AppImage (squashfs) and .deb. Note: Tauri
embeds the web bundle brotli-compressed in the binary; short denylist terms (4 letters) can by chance appear in that
high-entropy data and make the gate reject a build ("denylist#N ... in usr/bin/<binary>"). Another web bundle (any source
change) changes the bytes; do not allow-list the term.

Running: the AppImage needs FUSE 2 (`libfuse2` / `libfuse2t64`), otherwise `./<file>.AppImage --appimage-extract-and-run`.
The .deb (`sudo apt install ./<file>.deb`) pulls WebKitGTK 4.1 and the other dependencies. Details: `desktop/README.md`.

## iOS (on a Mac)
`[FLAVOR=…] scripts/build-ios.sh` runs on the build host and builds a **development-signed .ipa** on a Mac
(`ssh $MAC_HOST`, BatchMode), then publishes it for over-the-air install. `MAC_HOST`, `TEAM_ID` and `PUBLIC_BASE`
(`IOS_PUBLIC_BASE`) come from the environment or `$HUI_PRIVATE_DIR/build.env`. For `FLAVOR=personal` the overlay's
`app/` directory (identity + icons, no env files) is copied to the Mac as `~/$REMOTE_DIR/private/app`; a hermes build
checks the bundle id and scans the finished .ipa with the flavor guard.
```
scripts/build-ios.sh            # -> dist/share/ios/{hermes-ui.ipa,manifest.plist,index.html,signing.txt,icon-*.png}
                                #    dist/hermes-ui-ios-<sha>.ipa, dist/build-ios-<timestamp>.log
scripts/build-ios.sh --simulator   # unsigned Release build for the iOS Simulator (JS embedded, no Metro), nothing published:
                                   # dist/hermes-ui-ios-sim-<sha>.zip; installed + launched on SIM_DEVICE [iPhone 18 Pro]
scripts/ios-sim-smoke.sh           # UI smoke test of that build (fresh install, onboarding -> demo chat -> settings, iPad: landscape;
                                   # ⌘K/N/B are web-only) -> dist/ios-sim-smoke/<ts>/{NN-*.png,results.txt,app-errors.log,crashes.txt}
                                   # SIM_DEVICE="iPad Pro 13-inch (M5)" / "iPad Air 11-inch (M4)", HUI_LANG=de,
                                   # HUI_APPEARANCE=dark|light (reboots the simulator; status bar 9:41 for store drafts)
MODE=appstore scripts/build-ios.sh   # App Store / TestFlight .ipa -> dist/appstore/ (+ upload with ASC_* set), docs/IOS.md
MODE=appstore DRY_RUN=1 scripts/build-ios.sh   # only check inputs and print build number / upload plan
# source selection (device + simulator): default = clean worktree of HEAD
BUILD_REF=<commit> scripts/build-ios.sh …                       # another commit (e.g. when HEAD does not bundle)
scripts/build-ios.sh --working-tree …                           # current app/ files incl. uncommitted (label <sha>-dirty)
WORKING_PATHS="app/app.json app/plugins/x.js" scripts/build-ios.sh --working-tree …   # BUILD_REF + only these paths
```
The smoke test generates a throw-away Xcode project (`scripts/ios-sim/`: placeholder host app + `SmokeUITests.swift`,
made with the `xcodeproj` gem that CocoaPods brings) that drives the installed app by bundle id, so the app has no test
target. It needs no unlocked screen (simulators run headless). Screenshots are demo content only; still look at them
before copying any into `docs/`.
Install page: **`$PUBLIC_BASE/`**, e.g. `https://<build-host>.<tailnet>.ts.net/hermes/ios/` (tailnet only; `tailscale serve` maps `/hermes/` to
`dist/share/`). Open it in Safari on the iPhone and tap "Installieren" (it uses
`itms-services://?action=download-manifest&url=$PUBLIC_BASE/manifest.plist`).

Flow: clean `git worktree` of **HEAD** (uncommitted changes are not built, see `--working-tree`) → rsync `app/` to
`/Users/Shared/hermes-ui-build/app` (`REMOTE_DIR`, mode 700) on the Mac (without node_modules/.expo/android/ios/dist, **no `.env*`**, no keys) → `npm ci` (skipped when
package-lock.json is unchanged and node_modules was kept) → `expo prebuild -p ios --clean --no-install` →
`pod install` → `xcodebuild archive` (Release, `generic/platform=iOS`, own DerivedData under the build dir) →
export (method `debugging` = development) → manifest + install page → copy back into a staging dir → flavor guard +
release gate (`scripts/scan-artifact.sh`) → only then it replaces `dist/share/ios/` (a failed check publishes nothing
and leaves the previous install page in place).
Why `/Users/Shared/…` and not `~/builds`: the pods' `__FILE__` strings and the Hermes bytecode embed absolute build
paths, so a build under `/Users/<account>` puts the account name into the app (the flavor guard rejects that).
At the end the Mac is cleaned: DerivedData, archive, `ios/`, node_modules, and the npm (`$REMOTE_DIR/.npm-cache`,
the user's `~/.npm` is never touched, `$REMOTE_DIR/.npm-cache`), CocoaPods and `~/Library/Caches/ReactNative` download caches.
`KEEP_CACHE=1` keeps node_modules/Pods/caches (~2–3 GB, faster rebuild). The build refuses to start below
`MIN_FREE_GB` (8) free disk; peak usage during a build is ~3–4 GB (SDK 57 uses prebuilt React Native core and
precompiled Expo modules, so little is compiled). Only one iOS build at a time (`flock` on the build machine).

### Toolchain on the Mac (user-space, no sudo, no Homebrew, nothing in shell rc files)
| Path | What | Size |
|---|---|---|
| `~/.local/node` | Node 22 LTS (22.23.3), nodejs.org `darwin-arm64` tarball, SHA-256 checked against `SHASUMS256.txt` | ~190 MB |
| `~/.local/ruby` | Ruby 3.4.6, relocatable `portable-ruby` tarball from github.com/Homebrew/homebrew-portable-ruby (SHA-256 from the release digest). Homebrew itself is **not** installed | ~40 MB |
| `~/.local/cocoapods` | CocoaPods 1.16.2 (`GEM_HOME`), installed with that Ruby | ~25 MB |
| `/Applications/Xcode.app` | Xcode 27.0 (already there) | |

PATH/GEM_HOME are set only inside the remote part of the script. Why a separate Ruby: SDK 57 still uses CocoaPods
(the prebuild template has a Podfile), and its autolinking scripts use `Array#filter_map` (Ruby ≥ 2.7); the macOS
system Ruby is 2.6.10, so `pod install` fails there. Re-install / update:
```
# Node: download node-v22.x-darwin-arm64.tar.xz + SHASUMS256.txt from https://nodejs.org/dist/latest-v22.x/, shasum -a 256 -c, untar to ~/.local/node
# Ruby: portable-ruby-<v>.arm64_big_sur.bottle.tar.gz from the GitHub release, check digest, tar -xzf … -C ~/.local/ruby --strip-components=2
PATH=~/.local/ruby/bin:$PATH GEM_HOME=~/.local/cocoapods gem install --no-document 'concurrent-ruby:<1.3.4' 'xcodeproj:<1.26' cocoapods:1.16.2
```
Uninstall: `rm -rf ~/.local/node ~/.local/ruby ~/.local/cocoapods /Users/Shared/hermes-ui-build` (simulator app in `sim/`, ~70 MB, kept for `ios-sim-smoke.sh`).

### Signing
- Team `TEAM_ID` (your Apple developer team). Note: the id in parentheses in the certificate name "Apple Development:
  <Your Name> (<CERT_ID>)" is the personal certificate id, **not** the team id.
- `SIGNING=auto` (default): automatic signing with `-allowProvisioningUpdates`. Xcode then creates the explicit
  App ID of the build (`xyz.hermesui.app`, or the personal id) (with Push) and an Xcode-managed development profile containing **all devices registered in
  the team**. This needs the Apple ID in **Xcode → Settings → Accounts** on the Mac (one-time, see below).
- Without an account Xcode reports "No Accounts" and the script falls back to `SIGNING=local`: it uses the existing
  wildcard "iOS Team Provisioning Profile: \*" (only the devices registered when it was created), removes
  `aps-environment` from the generated entitlements in the build copy (the wildcard profile has no Push; the app only
  uses local notifications, so nothing is lost today) and, if `-exportArchive` refuses, zips the signed app from the
  archive. `signing.txt` next to the .ipa shows mode, profile, expiry, entitlements and the provisioned UDIDs.
- Keychain over ssh: an ssh login has its own security session in which the login keychain is locked, so
  `codesign` fails with `errSecInternalComponent`. The script tests signing first; if it fails, it runs the Mac part
  as a **one-shot LaunchAgent in the logged-in user's GUI session** (`launchctl bootstrap gui/<uid>`; the keychain is
  unlocked there), streams its log back and removes the agent afterwards (nothing stays in `~/Library/LaunchAgents`).
  Consequence: **someone must be logged in at the Mac** (screen may be locked, but the login keychain must not be
  locked, which is the default). No password is stored anywhere.
- `EXPORT_METHOD=release-testing` builds an Ad Hoc .ipa instead (no Developer Mode needed on the phones, but needs an
  Apple Distribution certificate, which automatic signing creates when the account is in Xcode).

One-time setup for full automatic signing:
1. On the Mac open Xcode → Settings (⌘,) → **Accounts** → "+" → Apple ID → sign in with the developer account.
   Team "<Your Name> (<TEAM_ID>)" must appear.
2. Re-run `scripts/build-ios.sh` (signing switches to `auto`).

### Registering another iPhone (e.g. a family member's)
A development/Ad-Hoc build only installs on devices whose UDID is in the profile.
1. Get the UDID: connect the iPhone by cable to the Mac → Finder → select the iPhone → click the line under its
   name until the UDID shows → right-click "Copy UDID". (Or: Xcode → Window → Devices and Simulators shows the
   "Identifier"; with the account in Xcode, connecting the phone and choosing "Use for Development" registers it
   automatically.)
2. Register it at https://developer.apple.com/account/resources/devices/list → "+" → Platform iOS, name, UDID.
   (Max. 100 iPhones per membership year.)
3. Re-run `scripts/build-ios.sh`. With the account in Xcode (`SIGNING=auto`) the regenerated profile includes the new
   device; check `signing.txt`. The `local` fallback cannot add devices.
Registered/paired devices on the Mac: `xcrun devicectl list devices`.

### Installing on the iPhone
1. iPhone must be in the tailnet (Tailscale app on) and registered in the profile (see above).
2. Open `$PUBLIC_BASE/` (e.g. `https://<build-host>.<tailnet>.ts.net/hermes/ios/`) in **Safari** → "Auf diesem iPhone installieren" → "Installieren".
3. Development builds need **Developer Mode** (iOS 16+): Settings → Privacy & Security → Developer Mode → on →
   restart → confirm. (The switch appears after a developer-signed app was installed or the phone was connected to
   Xcode once.) Ad-Hoc builds (`EXPORT_METHOD=release-testing`) don't need it.
4. The provisioning profile expires (see `signing.txt`); after that the app no longer starts until it is rebuilt
   and reinstalled.

cd app && npx eas-cli@latest login && npx eas-cli@latest build -p ios --profile preview

## Dev profiles
Shipped builds contain **no personal hosts, IPs or keys**: on first start the app shows onboarding, and the only
built-in connection is the offline demo (`demo://local`). For your own development builds you can pre-load
connections with `EXPO_PUBLIC_DEV_PROFILES` (JSON array, or a single object):

```
# app/.env.development.local  (NOT committed – add `.env*.local` to app/.gitignore)
EXPO_PUBLIC_DEV_PROFILES='[
  {"id":"dev-home","kind":"hermes","name":"Hermes zu Hause","baseUrl":"http://192.0.2.10:8642/v1","apiKey":"…","active":true},
  {"id":"dev-bridge","kind":"hermes","name":"Hermes (Bridge)","baseUrl":"https://bridge.example.org:8790/v1","apiKey":"<BRIDGE_TOKEN>","bridge":true},
  {"id":"dev-mock","kind":"hermes","name":"Mock-Server","baseUrl":"http://localhost:8787/v1","apiKey":"mock"}
]'
```
- Fields = `ConnectionProfile` (`app/src/settings/profiles.ts`): `kind` (`hermes` default | `demo`),
  `name`, `baseUrl`, `apiKey`, `model`, `bridge`, `sessionKey`, `syncSessions`, … plus `active: true` (default
  active profile on first start). `id` defaults to `dev-<n>`; keep ids stable, conversations are bound to them.
  Invalid entries are skipped (parser: `settings/devProfiles.ts`, tested).
- Dev profiles behave like built-ins: listed first, cannot be deleted; edits in Settings are stored on top of them and
  an empty stored key falls back to the dev key.
- Upgrading from builds that shipped presets: stored copies of the old presets keep their ids (`preset-bridge`,
  `preset-hermes-host`, …) and become normal profiles (migration v1 → v2 in `settings/migrate.ts`). To keep using the dev key
  for such a profile, give the dev profile the same `id`.
- **Why `.env.development.local`:** `EXPO_PUBLIC_*` values are inlined into the JS bundle. Expo CLI loads
  `.env.development*` only in development mode (`expo start`, debug builds); release bundles (`expo export:embed` /
  `scripts/build-apk.sh release`) run in production mode and read `.env.production*` / `.env` / `.env.local`, so the
  profiles are absent there. Never put them into `.env`, `.env.local` or `.env.production*`, and never into an EAS
  secret for a shared build. Settings shows a warning footnote whenever dev profiles are present in a bundle.
- The legacy variables `EXPO_PUBLIC_HERMES_API_KEY` / `EXPO_PUBLIC_HERMES_BASE_URL` / `EXPO_PUBLIC_BRIDGE_TOKEN` no longer
  create profiles (only the onboarding gate still treats the first and last as "set up already"); use the JSON above.

## Web-App (PWA)

The app also runs on react-native-web. `scripts/build-web.sh` exports it as a static, installable web app
(PWA) – the primary way to use it on an iPhone without the App Store.

### Build

```bash
scripts/build-web.sh                                             # official build -> dist/web/
FLAVOR=personal scripts/build-web.sh --brand "$HUI_PRIVATE_DIR/web/<name>.env"   # e.g. a branded PWA -> dist/web-personal/
# → dist/web/  (index.html, manifest.webmanifest, sw.js, icons/, _expo/static/…, assets/…)
```

Release asset: `scripts/package-web.sh` packs the official `dist/web` into `dist/release/hermes-ui-plus-web-<version>.tar.gz` + `.sha256` (refuses non-hermes builds, runs the release gate; `VERSION=` overrides the version from `bridge/package.json`). Install guide for users: [WEB-APP.md](WEB-APP.md).

- Same safety model as the APK build: clean copy in `~/builds/hermes-ui-web` (rsync, `.env*` excluded so dev
  profiles never end up in a web bundle), `node_modules` hard-linked from `app/node_modules` when the lockfile is
  identical (else `npm ci`, force with `NPM_CI=1`), `expo export -p web` inside a systemd user scope with
  `MemoryMax=4G MemorySwapMax=0`, one web build at a time, refuses to start below `MIN_AVAIL_GB` (5) free.
  Log: `dist/build-web-<ts>.log`.
- Env: `EXPO_PUBLIC_APP_NAME` (default `Hermes Interactive UI+`; personal: from `app/personal.env` / the brand file), `EXPO_PUBLIC_APP_SHORT_NAME` (home-screen label + header, default `Hermes UI+`, keep ≤ 12
  chars; personal web builds without `--brand` get the overlay icon), `EXPO_PUBLIC_THEME_COLOR` / `EXPO_PUBLIC_THEME_COLOR_DARK`, `WEB_SW=0` (no service worker),
  `MEM_MAX`, `MAX_WORKERS`. `EXPO_PUBLIC_*` values are inlined into the bundle – **never put tokens there**.
- How it works: `web.output` is unset = `single` (one SPA `index.html`). Expo uses `app/public/index.html` as
  the HTML template and copies `app/public/` into the export (Expo PWA guide: docs.expo.dev/guides/progressive-web-apps).
  The template carries the PWA head: `viewport-fit=cover` (safe areas via `env(safe-area-inset-*)`, which
  react-native-safe-area-context reads on web), `apple-mobile-web-app-capable`, status bar style `default`
  (opaque, readable in light and dark), `theme-color` (light/dark), manifest + `apple-touch-icon`, no page
  bounce (`overscroll-behavior: none`), and inputs forced to 16 px on iOS (Safari zooms into smaller inputs on
  focus). `scripts/web-finalize.mjs` then writes name/short name/colours into `index.html` + `manifest.webmanifest`
  and registers `sw.js`.
- Icons: `app/public/icons/` (192, 512, maskable 512, apple-touch-icon 180), generated from `app/assets/icon.png`
  with ImageMagick (`convert assets/icon.png -resize 180x180 public/icons/apple-touch-icon.png`, …). Replace
  them for a personalised icon.
- Service worker (`app/public/sw.js`, only registered on secure origins): caches the app shell only (index.html,
  manifest, icons, the content-hashed `/_expo/static/` and `/assets/` files); navigations are network-first, so a
  new deploy shows up on the next start. It never touches `/v1`, `/api`, other origins or non-GET requests.
- The manifest has **no `start_url`** on purpose: it defaults to the URL the app was added from, so an iPhone
  that adds the app while the pair link is open keeps the link as start URL and shows its connection screen on the first launch
  (already applied links are remembered and skipped afterwards).
- Streaming: `expo/fetch` is `globalThis.fetch` on web; SSE is read via `ReadableStream` (`res.body.getReader()`),
  supported by iOS Safari ≥ 16. A cross-origin API must send CORS headers (`Access-Control-Allow-Origin`,
  `-Headers: authorization, content-type`); serving the app from the API's origin avoids CORS completely.
- Keys on web: expo-secure-store has no web implementation, so keys are stored in `localStorage` of the app's
  origin (plain text, see the note in `app/src/settings/storage.ts`). Serve the app only on a trusted origin
  (tailnet + HTTPS, no third-party scripts) and use a scoped, revocable token for web profiles. iOS keeps the
  storage of a home-screen web app separate from Safari's.

### Hosting (tailnet)

Option A – the API host serves the bundle itself (e.g. the UI bridge with `BRIDGE_WEB_DIR`: `/` = `dist/web`, `/v1` = API).
Same origin: no CORS, and the pair link can omit `u=` (the app uses `<page origin>/v1`). Any static file
server works as long as `index.html` is served for `/` and `.webmanifest` gets `application/manifest+json`.

Option B – `tailscale serve` on a host (generic placeholders):

```bash
rsync -a --delete dist/web/ <host>:~/hermes-web/
ssh <host> 'tailscale serve --bg --https=443 ~/hermes-web'          # → https://<host>.<tailnet>.ts.net/
# API on the same host under /v1 (same origin):
ssh <host> 'tailscale serve --bg --https=443 --set-path=/v1 http://127.0.0.1:<api-port>/v1'
ssh <host> 'tailscale serve status'
```

HTTPS matters: service workers, `isSecureContext` and "Add to Home Screen" as a standalone app need it; the
`*.ts.net` certificate is automatic. Only tailnet members can reach `tailscale serve` (not `funnel`).
Local check: `python3 -m http.server -d dist/web 8102` → http://localhost:8102 (localhost counts as secure).

Pairing the web app (including on an iPhone, Safari → Share → Add to Home Screen): [WEB-APP.md](WEB-APP.md).
