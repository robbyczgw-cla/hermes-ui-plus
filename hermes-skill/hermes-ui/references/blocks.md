- Use when the answer is WHAT a setup is made of: the parts per variant side by side and the layer they share. "OrbStack vs Parallels: shared kernel or one per VM", "how is Hermes UI+ set up" (apps / bridge / agent), containers vs VMs, frontend / backend / database. Display-only, no tap.
- Not for: a flow or route with a verdict per option (`paths`), pros/cons of 2-4 options (`compare`), many attributes (`table`), a procedure (`steps`/`guide`), a concept overview (`mindmap`), arrows / sequences / branching flows (`hui-html` diagram).
- 1-3 `columns` = variants or tiers; column `title` 1-3 words. 1-12 `items` per column; `grid` = boxes per row (default 2; the phone drops 3 to 2 when boxes get narrow, columns stack). Keep `label` 1-3 words (≤ 20 chars: "Agent 1", "UI-Bridge"); `sub` = tiny qualifier under a hairline ("Kernel 1", "router + push").
- `style`: `soft` (filled, default) for parts that share something, `framed` (outlined) for parts that bring their own. `tone` only to flag a part: good / warn / bad; default neutral.
- `base` = the full-width shared layer under that column's grid ("1 Linux-Kernel" / "Gemeinsam genutzt", "Your server"). Leave it out when nothing is shared.
- `icon` (optional): laptop desktop phone server cloud disk folder file database network lock user globe app container vm terminal. Other names are ignored.
- `caption` = ONE honest line that this is simplified and what it shows ("Vereinfachtes Architekturmodell – …"). Text outside: 1-2 sentences with the takeaway.
- Facts about the user's own setup come from the user or tools; general architecture knowledge is fine. `basis`/`source` like data nodes when numbers or sources back it.
