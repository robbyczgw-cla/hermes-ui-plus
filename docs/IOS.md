# iOS: web app now, App Store / TestFlight later

Status 2026-10-13: the native iOS app builds and runs (simulator, development-signed devices). It is **prepared for
TestFlight and the App Store, nothing is submitted**. Submitting needs the owner's paid Apple Developer Program
membership, an App Store Connect app record and (for scripted uploads) an App Store Connect API key. Until then
iPhone and iPad users use the web app (PWA).

Related: [STORE.md](STORE.md) (store questionnaires, listings, review policy notes), [BUILD.md](BUILD.md) "iOS
(Mac)" (toolchain, signing, simulator), [WEB-APP.md](WEB-APP.md) (PWA install guide), [../PRIVACY.md](../PRIVACY.md).

## 1. What works today without an Apple account: the web app (PWA)

The web app is the same app as the native one, served by the user's own bridge. On iPhone/iPad:

| Requirement | State |
|---|---|
| Install: Safari → Share → **Add to Home Screen** (HTTPS origin, e.g. Tailscale `https://<host>.<tailnet>.ts.net`) | works; `manifest.webmanifest` has `display: standalone`, `id`/`scope` `/` |
| Home-screen icon | `apple-touch-icon` 180×180, opaque (iOS rounds the corners itself), from `app/brand/icon/petasos.svg` |
| Full screen without Safari UI | `display: standalone` + `apple-mobile-web-app-capable` (older iOS) |
| Name under the icon | `apple-mobile-web-app-title` = short name ("Hermes UI+", set by `scripts/web-finalize.mjs`) |
| Status bar | `apple-mobile-web-app-status-bar-style: default`: opaque bar, content starts below it, readable in light and dark |
| Notch / home indicator | `viewport-fit=cover`; the app pads with `env(safe-area-inset-*)` through `react-native-safe-area-context` |
| Colours | `theme-color` light/dark = `colors.paper` / `colors.ink` (official build) |
| Inputs | font size ≥ 16 px on iOS, so Safari does not zoom into the composer |
| **Web Push** | iOS/iPadOS **16.4+**, **only in the home-screen app** (not in a Safari tab), permission asked from a tap (settings switch), VAPID keys on the bridge. The service worker (`app/public/sw.js`) shows a notification for every push unless a visible, focused window of the app takes it |
| Offline shell | service worker precaches the app shell (`hui-shell-*` caches) |

Known limits of the PWA on iOS: separate storage from Safari (pair inside the installed app, WEB-APP.md section 3),
no background execution (an answer only continues while the app is open), no Siri/share-sheet integration, the
manifest `orientation` is ignored by iOS (the PWA rotates on iPad).

**Silent pushes on WebKit (handled):** WebKit expects every push to show a notification and may revoke the
subscription of a site that receives "silent" pushes. `sw.js` therefore always calls `showNotification` on WebKit,
also when the app is open and focused (it closes that notification right away and hands the push to the window).
Still to confirm on a real iPhone over a longer period; the simulator cannot verify it.

## 3. Versions and build numbers

- `app.json` `version` stays the product version (`0.1.0-alpha.1`): shown in the app (Settings → About), used for
  Android `versionName`, reports and the web build.
- App Store Connect only accepts 1–3 dot-separated integers as `CFBundleShortVersionString`. `plugins/withIosRelease.js`
  sets `ios.version` to the numeric core: `0.1.0-alpha.1` → **`0.1.0`** (also for development and simulator builds).
  The alpha/beta status is expressed by TestFlight itself, not by the version string.
- `CFBundleVersion` (build number) must grow for every upload of the same version. `ios.buildNumber` in `app.json`
  is the default for local builds; `MODE=appstore` takes the next number from the private counter file
  `$HUI_PRIVATE_DIR/ios-build-number` (one integer = last used number) and writes it back once the `.ipa` passed the
  release gate. `BUILD_NUMBER=<n>` overrides it (e.g. to re-upload a build whose upload failed).
- For the next marketing version, bump `version` in `app.json` (and `app/package.json`), e.g. `0.2.0-alpha.1` → iOS `0.2.0`.

## 4. Building

```
SIM_DEVICE="iPhone 18 Pro Max" scripts/build-ios.sh --simulator   # unsigned Release build for the simulator
SIM_DEVICE="iPad Pro 13-inch (M5)" scripts/ios-sim-smoke.sh        # UI smoke test + screenshots (demo mode)
MODE=appstore DRY_RUN=1 scripts/build-ios.sh                        # check inputs, print build number + upload plan
MODE=appstore scripts/build-ios.sh                                  # App Store .ipa -> dist/appstore/
ASC_KEY_ID=… ASC_ISSUER_ID=… ASC_KEY_PATH=…/AuthKey_<id>.p8 MODE=appstore scripts/build-ios.sh   # + validate + upload
ASC_UPLOAD=0 ASC_KEY_ID=… ASC_ISSUER_ID=… ASC_KEY_PATH=… MODE=appstore scripts/build-ios.sh   # key for signing only, no upload
```

`MODE=appstore` (same as `--appstore`), on top of the device flow in BUILD.md:
1. official flavor only, from a commit (HEAD or `BUILD_REF`), never `--working-tree`;
2. prebuild with `HUI_IOS_BUILD_NUMBER=<next>` and `HUI_APS_ENV=production`; refuses a non-numeric version, a wrong
   build number or a non-production `aps-environment`;
3. `xcodebuild archive` (Release, automatic signing, `-allowProvisioningUpdates`, plus `-authenticationKey*` when the
   API key is given) and export with method **app-store-connect** (`uploadSymbols`, `manageAppVersionAndBuildNumber
   = false`, `destination = export`);
4. checks the exported app: distribution-signed, `aps-environment = production`, `get-task-allow = false`; prints no
   team id, profile or certificate details;
5. copy back → flavor guard → `scripts/scan-artifact.sh` (signature blobs are skipped as for development builds) →
   `dist/appstore/hermes-ui-<version>-<build>-<sha>.ipa` → counter written;
6. only with `ASC_KEY_ID`, `ASC_ISSUER_ID` and `ASC_KEY_PATH`: `xcrun altool --validate-app`, then `--upload-app`
   on the Mac. The key goes to `$REMOTE_DIR/asc` (mode 700/600) only for this run and is deleted afterwards (also on
   failure). Without the variables the script prints the manual next steps (Transporter or altool).

First real run (2026-10-14, commit f10723a, `ASC_UPLOAD=0`): archive + export with an App Store Connect API key of
role **App Manager** and **no** Apple ID in Xcode worked. Xcode cloud signing used a cloud-managed Apple Distribution
certificate (no distribution certificate in the account list or the Mac keychain was needed), the App Store profile
was created on the fly. Result: `hermes-ui-0.1.0-1-<sha>.ipa`, 25 MB, distribution-signed, `aps-environment =
production`, `get-task-allow = false`, release gate clean, counter = 1. Validate/upload not run yet: there is no App
Store Connect app record (section 5, step 4).

## 5. TestFlight checklist (owner steps)

1. **Apple Developer Program** (paid, organisation or individual). The seller name shown in the store is the
   account holder's name (individual) or the organisation.
2. **Identifiers:** developer.apple.com → Certificates, IDs & Profiles → Identifiers → App ID `xyz.hermesui.app`
   with the **Push Notifications** capability. **Done 2026-10-14** via the App Store Connect API (App Manager key):
   explicit App ID registered, Push Notifications enabled.
3. **Xcode on the Mac:** Xcode → Settings → Accounts → add the Apple ID of the paid team, so automatic signing can
   create the Apple Distribution certificate and the App Store profile. Alternative: an API key (step 5), used by
   the script for cloud signing; an **App Manager** key was enough (section 4). Only if cloud signing is ever refused:
   Xcode → Settings → Accounts → team → Manage Certificates → "+" → Apple Distribution (on the build Mac), or an Admin key.
4. **App Store Connect → My Apps → "+" New App:** platform iOS, name "Hermes Interactive UI+" (check availability;
   STORE.md section 7 on the name), primary language German or English, bundle id `xyz.hermesui.app`, SKU e.g.
   `hermes-ui-plus`, user access full.
5. **API key** (optional, for scripted upload): App Store Connect → Users and Access → Integrations → App Store
   Connect API → Team Keys → "+" (role **App Manager** for upload; **Admin** if the script should also do cloud
   signing). Download `AuthKey_<id>.p8` once, store it in `$HUI_PRIVATE_DIR` (never in the repo), note key id and
   issuer id.
6. Build and upload: `MODE=appstore scripts/build-ios.sh` with `ASC_*` set, or without and upload the `.ipa` with
   Transporter.
7. App Store Connect → TestFlight: wait for processing (5–30 min). Export compliance needs no answer
   (`ITSAppUsesNonExemptEncryption = NO`). Fill in **Test Information** (feedback e-mail, beta description, the
   review notes of section 6 for external testing).
8. **Internal testing** (up to 100 team members): immediately, no review. **External testing** (public link or
   e-mail invites, up to 10,000): needs Beta App Review of the first build.
9. Before the App Store submission: App Privacy (section 8), age rating (STORE.md 3.3), privacy policy URL
   `https://hermesui.xyz/privacy`, support URL, screenshots (section 10), description/keywords (STORE.md 4),
   reviewer access (section 6).
10. Push in production: create an APNs auth key (`.p8`, Keys → "+" → Apple Push Notifications service) and configure
    it on the bridge (SELF-HOSTING.md "Push notifications"). Each self-hoster needs the **developer's** APNs key to
    push to the store app, which is a design question (STORE.md 6, last item): without it the store app works but
    receives no remote pushes.

## 7. Export compliance

Answer: **the app uses only encryption exempt from export documentation.** `ITSAppUsesNonExemptEncryption = NO` is
in the Info.plist, so App Store Connect asks nothing per build. Reasoning (STORE.md 3.4): HTTPS/TLS through the OS
(`URLSession`), Keychain through `expo-secure-store`, hashing and random numbers through `expo-crypto`; no own or
non-standard cryptography. Re-check if the app ever adds its own encryption (e.g. end-to-end encryption).

- **Data Used to Track You:** none. **Tracking:** No (no ATT prompt, no tracking domains).

## 9. Open items and decisions for the owner

- **State 2026-10-14:** Developer Program, API key (App Manager), App ID `xyz.hermesui.app` + Push: done. First App
  Store build (0.1.0, build 1) archived, signed and gated, **not uploaded**. Missing, owner only (Apple allows it in
  the web UI only): the **App Store Connect app record** (section 5, step 4: App Store Connect → Apps → "+" → New
  App → iOS, name "Hermes Interactive UI+", bundle id `xyz.hermesui.app` from the list, SKU, full access). Then
  `MODE=appstore scripts/build-ios.sh` with `ASC_*` set builds the next number and uploads; afterwards TestFlight →
  Internal Testing → add the internal group/testers. APNs auth key for production push still open (section 5, step 10).
- Reviewer Hermes instance + pairing link (section 6).
- ATS: keep `NSAllowsArbitraryLoads` (needs the justification in the review notes) or switch to
  `NSAllowsLocalNetworking` + HTTPS-only for non-local hosts (breaks plain-HTTP servers reachable by IP over a VPN).
- Calendar: the app asks for **full** calendar access (`expo-calendar/legacy` reads the calendar list to pick the
  default calendar). Write-only access (`NSCalendarsWriteOnlyAccessUsageDescription`, iOS 17+) would be a smaller
  ask; it needs a code change in `src/actions/calendar.ts`.
- Deployment target 26.0 excludes iPhones that cannot run iOS 26 (section 2).
- App Store availability on Apple silicon Macs ("Designed for iPad") and visionOS: decide in App Store Connect →
  Pricing and Availability; untested.
- Optional: dark and tinted app icon variants (`ios.icon` with `light`/`dark`/`tinted`), today one icon for all.
- Web Push on iOS while the app is focused: handled in `sw.js`, still to confirm on a real device over time (section 1).
- Hardware-keyboard shortcuts on iPad (⌘K search, ⌘N new chat, ⌘B sidebar): web-only today; native needs `UIKeyCommand`
  support (a small native module or a library).
- **Status bar style on iOS 27:** `UIApplication setStatusBarStyle` is a no-op from iOS 27 on (the simulator logs
  "deprecated and is a no-op on 27.0 and later"), and `expo-status-bar` / React Native's `StatusBar` use exactly that
  (with `UIViewControllerBasedStatusBarAppearance = NO`). The status bar then follows the **system** appearance. That
  is right whenever the app theme follows the system (the default), but wrong when the user picks an explicit
  light/dark mode or a single-scheme theme ("OLED black") that differs from the system, and in the black image
  viewer in light mode (dark text on black). Fix options: wait for Expo/React Native to adopt view-controller-based
  status bar appearance, or set the window's `overrideUserInterfaceStyle` from the effective theme (also makes
  keyboard and system sheets match the theme). Not changed yet.

Notes from the runs:
- The iOS 27 simulator applies a changed system appearance to running apps only after a reboot (system Settings
  stays light too), so live light/dark switching could not be verified; `ios-sim-smoke.sh` sets it before booting.
- The demo's loan calculator (sandboxed HTML) is German in every language (by design, the answer says so); prefer
  chart, comparison and report for English store screenshots.
- The chat list preview of a demo chat shows the placeholder text "[Component]" for interactive blocks
  ("Overview [Component] Trend …"), visible in the iPad sidebar. Intended (covered by `messages.test.ts`), but it
  reads oddly; a localised word ("chart", "table") would look better. Cosmetic, all platforms.
- `expo-notifications` logs a keychain entitlement error in the unsigned simulator build (expected; signed builds
  have the keychain access group).
