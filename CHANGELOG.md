# Changelog

All notable changes are documented here. The format follows [Keep a Changelog](https://keepachangelog.com), and the project aims to follow [Semantic Versioning](https://semver.org).

## 0.1.0-alpha.1 - 2026-10-15

First public alpha of Hermes Interactive UI+ ("Hermes UI+" on the home screen): interactive chat for Hermes Agent and an unofficial community client, not affiliated with Nous Research. Requires Hermes Agent v0.21 or newer; tested with Hermes v0.22.0 (see Known limitations for two upstream Hermes issues). Expect rough edges and changes between alphas.

### Added

- **Chat** with streaming answers, progressive Markdown, a tool-call timeline, multiple conversations stored on the device, and light and dark themes. The default look is "Bote" (ink, ivory and brass); further themes include Graphit, Papier, Wald, OLED, Nord, Solarized and Rose, with a colour-blind-checked chart palette and at least 4.5:1 contrast for text in every theme.
- **Interactive answer components** (48 native node types, layout and text nodes included): tables, charts (bar, line, area, pie, donut, radar, gauge, heatmap, waterfall, scatter and more), stats, comparisons, steps, timelines, forms, choices, checklists, calculators, maps, recipes, quizzes, flashcards, timers, polls, agendas, decisions, rankings, scales, translations, weather, places, products, guides, workouts, study plans, vocabulary, mind maps and the two newest, **paths** and **blocks** (below). Your interaction is sent back to Hermes as the next message and state is kept per conversation.
- **The `hermes-ui` skill** for Hermes Agent, loaded only for sessions from the app, so other Hermes clients are unaffected.
- **UI-Bridge** (Node 22, `npx hermes-ui-plus-bridge` or Docker) with a guided `setup` wizard: presentation router (rule-based), streaming pass-through, uploads with size and type limits, push, and serving of the web app. By default the bridge is a **pure pass-through to Hermes**: it calls no model or search provider itself, the wizard asks for no provider keys, and the startup log says `direct providers: none (pure Hermes pass-through)`. Optional direct-provider extras are opt-in with `setup --extras` (or a "y" to the wizard's extras question): LLM router (Claude, Jev), generated titles and follow-ups, image search (Serper, Brave) and voice (Groq, OpenAI, Deepgram, ElevenLabs). These call providers from the bridge, outside Hermes; the startup log names each active one. A provider key alone switches nothing on: the model router needs `ROUTER_BACKEND`, titles and follow-ups need `BRIDGE_META=on`, so an `ANTHROPIC_API_KEY` exported in your shell is never used by accident. The Docker image contains the skill's bootstrap message (build it after `npm run bundle-skill`), and the bridge warns at startup if that message is missing. The npm package ships the MIT license. A later version will move these extras into a Hermes plugin. Re-running `setup` keeps all existing keys and `ROUTER_BACKEND`.
- **Pairing and device tokens:** pairing by QR code or link, a revocable token per device, one-time codes for remote pairing, and `devices list/add/revoke`.
- **Approvals:** answer Hermes approval requests in the app, in the web app also from a Web Push notification. When Hermes smart approval auto-approves a flagged command, the tool timeline says so.
- **Hermes profiles (bots):** pick a Hermes profile (own model, memory and skills) per chat in the model menu's "Bot" section. The chat talks to `/p/<profile>/…`, the drawer marks non-default bots, session sync, approvals and push open the right bot. The UI-Bridge forwards the same allow-list under `/p/<profile>/`, lists bots at `GET /bridge/profiles` (`BRIDGE_PROFILES`: `auto`, a list or `off`); direct connections enter their bots in the connection settings. Without profiles nothing changes: no "Bot" section, and an older bridge without `GET /bridge/profiles` simply has no bots. The offline demo shows a second sample bot.
- **Schnellfrage (quick questions, ⚡):** with the optional Hermes plugin `hermes-ui-plus` and the bridge, a fast model of your Hermes answers one-off questions in about two seconds, without the agent (no memory, tools or live data). ⚡ in the composer switches to one local quick thread per connection (kept on the device for 24 hours, not in your Hermes history); long-press on Send sends a question there directly. Answers render interactive cards and show "⚡ model · time". "Mit Hermes weitermachen" opens a normal Hermes chat with the question and answer as context. Settings → Schnellfrage: model from Hermes' catalog, limits, the ⚡ switch. Without the plugin nothing changes: no ⚡, no extra requests. The plugin is experimental: it uses one internal Hermes function for the model call (docs/HERMES-PLUGIN.md). The offline demo has prepared quick answers.
- **Slash commands** with a searchable palette: `/new`, `/model`, `/reasoning`, `/fast`, `/retry`, `/stop`, `/approve`, `/deny`, `/title`, `/search`, `/skills`, `/branch`, `/usage`, `/status`, `/export`, `/delete`, `/help`.
- **Voice:** dictation and read-aloud, on the device, through the bridge, or with your own provider key in the app.
- **Images and attachments:** photos and documents in messages, image lookups with source credit, and tap-to-load for images from unknown hosts.
- **Image privacy setting:** "Images from unknown sites" has three honest options: *Via bridge (recommended)* (the default: product and place photos load at once through the bridge's image proxy, so the site sees the bridge instead of your phone, other unknown images wait for a tap), *Only after tap* (every image from an answer waits for a tap, and still loads through the bridge afterwards) and *Always load*.
- **Product, place and event photos without provider keys:** the `hermes-ui` skill asks Hermes' extract tool for page images (`web_extract_plus` `include_images`) and puts the page's main image (`og:image`) into the card. The app loads it through the bridge's new **image proxy** (`GET /bridge/img`, no keys, `BRIDGE_IMAGE_PROXY=off` to disable), so it shows at once and the image host never sees your phone's IP address. If it fails, the card shows a calm fallback; products, compare columns and web-sourced images never fall back to a Wikipedia / Wikimedia guess by name (only places and other encyclopedic subjects use that lookup). With image loading switched off nothing is loaded. See [docs/BRIDGE.md](docs/BRIDGE.md#image-proxy).
- **Sandboxed HTML widgets** for custom visuals, with no access to your data or device.
- **Push notifications:** Web Push for the web app (PWA), including the iPhone/iPad home-screen app; message previews off by default. FCM / APNs only for self-built apps.
- **Tables on phones:** a table that cannot fit the phone width turns into one card per row; on Android the layout (fill the width, row cards or horizontal scroll) is decided before rendering, with hyphenation for long words.
- **First turn follows the skill:** the app's first message makes Hermes load the `hermes-ui` skill on the first real question and lead with the result instead of a wall of Markdown. With the bridge, the skill's core text comes inline right after that message on every app turn (cached, about 2k tokens; `BRIDGE_SKILL_INLINE=off` to disable), so models that skip loading the skill (seen with Claude Sonnet) still render components and follow the router hint. See [docs/BRIDGE.md](docs/BRIDGE.md#skill-core-inline).
- **Compare cards:** pros and cons are marked only when the answer says so explicitly (check for a pro, minus for a con); everything else stays a neutral fact.
- **Follow-up suggestions:** the `hermes-ui` skill ends informative answers with up to three follow-up questions, shown as a vertical list. The setting "Follow-up suggestions" turns them off; Hermes is then told to skip them.
- **Events and "what's on" questions** route to place cards with photos.
- **Live-data answers search first:** for product, place and weather questions the router tells Hermes the answer needs live data, and the `hermes-ui` skill no longer lets it answer from memory without searching first.
- **`paths` answer component:** 2-6 ways, variants or architectures ("where do the files live", "how does a request travel") as one card: title, verdict badge (neutral, good, warn, bad), a chain of node pills joined by arrows, one note line. Optionally a single choice that sends your pick back. The router recognises these questions and the `hermes-ui` skill documents the format.
- **`blocks` answer component:** an architecture or setup at a glance: one card with up to three columns (variants or tiers) of labelled boxes, an optional shared base layer and a caption. Columns sit side by side on tablets and desktop and stack on a phone. Display-only; router format and skill reference included.
- **Typed component fences** (for example ```` ```suggestions ````) render as cards.
- **Platforms:** Android APK (64-bit ARM, Android 7.0+), web app (PWA, installable to the home screen, see [docs/WEB-APP.md](docs/WEB-APP.md)), macOS app and Linux AppImage / .deb (below). German, English and Spanish UI; the web app's `<html lang>` follows the UI language. The iOS app is prepared for TestFlight / App Store (release configuration, numeric marketing version) but not distributed yet.
- **macOS app** (Tauri, Apple Silicon, macOS 13+; Developer ID signed and notarized): native look with a translucent sidebar, unified title bar and the system accent colour; menu bar with keyboard shortcuts (new chat, search chats, find in chat, stop, copy last answer, switch chats) and a native right-click menu on answers; dock badge for unread answers and a dock menu with the newest chats; notifications for finished answers, inbox and approvals, with *Allow once* / *Deny* buttons that answer without opening the window; open at login, menu-bar-only mode, optional Touch ID lock; files by drag and drop, onto the dock icon or paste; global shortcut Option+Space. Microphone and camera work under the hardened runtime. See [desktop/README.md](desktop/README.md).
- **Linux app (alpha):** AppImage and .deb for x86_64, built on Ubuntu 22.04 so they run on glibc 2.35 or newer (Ubuntu 22.04+, Debian 12+). Not signed, no auto-update; tray icon and Alt+Space depend on the desktop environment. See [desktop/README.md](desktop/README.md#linux-alpha).
- **Instant chat switching:** transcripts are cached and Hermes chats you have not opened yet are fetched ahead, so a switch shows header, composer and the answers on the first frame; a chat opened for the first time shows that it is loading instead of a blank screen. Reopening a chat reuses the parsed answers, and cold start reads the crash marker and the open chat in parallel.
- **Send while uploading:** with a bridge, Send works while attachments still upload. The message appears at once with per-file progress and the turn starts when the last upload is done (cancel, retry or remove a failed file from the bubble). Picked photos join the tray and start uploading one by one.
- **Read-aloud while streaming:** "Read replies aloud automatically" starts with the first complete sentences instead of waiting for the finished answer.
- **Faster dictation:** recording starts on touch-down (tap to start and stop, or hold to talk), so the first words are no longer cut off; permission and consent are not re-checked on every start.
- **Older chats and the "Chats" setting:** at the end of the drawer the app loads older Hermes chats on demand ("Load older chats"), so older app chats are reachable on a new device. Settings → Chat → **Chats** shows either this app's chats from all your devices (default) or only those created on this device (view filter, nothing is deleted). The drawer order follows the server's activity: opening a chat no longer moves it to the top.
- **Smoother streaming:** hot paths of the stream parser, Markdown, partial-JSON repair and list updates were optimised, so long answers and long chats stay responsive.
- **Setup wizard, first install:** a clear Node.js 22 check, a container mode (Hermes in Docker or Podman: prints the start command instead of installing a service), and a local web link for a first test without HTTPS.
- **Connection resilience:** recovery after going offline has hard deadlines, stalled live inboxes reconnect, slow links no longer count as offline, and answers finished while the connection was lost are recovered.
- **Release integrity:** the official release APK is always signed with the release key (published fingerprint in README), and APK and web bundle come with SHA-256 checksum files.
- **Build number:** every Android build carries a running build number as its `versionCode`, so each APK installs over every older one. Settings → About shows "<version> · Build <n>" with the source commit.
- **Google Play bundle:** `BUNDLE=1 scripts/build-apk.sh release` builds an Android App Bundle signed with the same release key, for a later Play upload (docs/STORE.md, docs/RELEASING.md). Nothing is on Google Play yet.
- **No duplicate turns, resumable answers (UI-Bridge):** every message carries an `Idempotency-Key`. A retry of a send whose connection broke before any answer arrived never asks Hermes twice, and an answer whose stream broke off continues where it stopped (`X-Hermes-UI-Resume-Offset`) instead of waiting for the finished turn. Bounded in-memory buffer, `BRIDGE_RESUME=off` to disable; see [docs/BRIDGE.md](docs/BRIDGE.md#idempotent-send-and-resume) and [docs/adr/0002-resumable-runs.md](docs/adr/0002-resumable-runs.md).
- **Hermes v0.22 model lock:** a model picked for a chat is locked on its Hermes session (`POST /api/sessions/{id}/model`), so Hermes keeps it across restarts and for its own session clients; the header shows "· locked". Older Hermes versions are detected and skipped. Streamed reasoning ("thinking") also shows for non-streaming answers.
- **CI** runs the type check and all app, bridge, push and script test suites plus the leak checks on every push.
- **Documentation:** README, self-hosting guide, web app install guide, privacy policy, security policy, contributing guide, protocol specification, build guide and release procedure.

### Security

- **Image proxy hardening (bridge):** `GET /bridge/img` needs a device token and fetches only public `https` hosts on port 443: every resolved address and every redirect (at most 3) is checked against private, loopback, link-local, CGNAT, unique-local, multicast and reserved ranges, and the connection goes to exactly the checked address (no DNS rebinding). Only JPEG, PNG, WebP, GIF and AVIF (checked by magic bytes, never SVG), at most 8 MB, 5 s connect / 15 s total; no client headers, cookies or referrer go out; rate limited per device; logs show only host, status, size and duration.
- **One-time pair codes (bridge):** pair links and QR codes carry a one-time code (`c=`, 32 random bytes, stored only as a hash) instead of a device token. The app trades it once for its token with `POST /bridge/pair/redeem`; the token is created only then. Codes expire after one hour, a second use or an unknown code gets the same `410` answer, redeem is rate limited, and codes and tokens are never logged. `devices add`, `--pair`, the pairing page and the setup wizard print the new links; they never contain a token.
- **Pairing fails closed (bridge):** without a state directory the bridge refuses to pair instead of putting `BRIDGE_TOKEN` into the link. `BRIDGE_PAIR_ADMIN_TOKEN=1` restores the old, unsafe behaviour.
- **Device list writes are locked (bridge):** the bridge, the CLI and the setup wizard change `devices.json` under an exclusive lock file, so a `devices revoke` can no longer be overwritten by the running bridge. State files are written through unpredictable temp names opened exclusively.
- **Pass-through limits (bridge):** the short Hermes routes time out after 30 s (`BRIDGE_UPSTREAM_TIMEOUT_MS`) and cap request bodies (approval answers 8 KB); `/health` forwards no body; clients must send a complete request within `BRIDGE_REQUEST_TIMEOUT_MS` (5 min, headers 30 s) while long streamed answers stay unlimited. Only an allow-list of request headers reaches Hermes, and `Set-Cookie` from Hermes is dropped.
- **Upload quota (bridge):** the upload folder is capped at `BRIDGE_UPLOAD_QUOTA_MB` (default 500; expired files are deleted first, then 507), with at most 2 uploads per token and 6 in total at once.
- **Bounded SSE observers (bridge):** the bridge's own stream observers skip a single SSE line or event over about 1 MiB and log only its size; the app still receives the stream unchanged.
- **Content-Security-Policy for the web app (bridge):** pages served from `BRIDGE_WEB_DIR` carry a CSP (no plugins, no framing, no `<base>` hijack, forms only to the bridge, no plain-http connections or images). `BRIDGE_WEB_CSP=report-only|off` for troubleshooting.
- **Push senders do not follow redirects (bridge):** Web Push and FCM requests treat a 3xx as a failure.
- **Single-use pair links (app):** the app redeems the one-time code in a pair link (`c=`, `POST /bridge/pair/redeem`) for its own device token and does not keep the code; an expired or already used link shows "Pairing link expired or already used".
- **Model-provided messages are confirmed centrally:** a `send` / `ask` from an answer goes out with one tap only when the tapped chip or button shows exactly that text (or a module composed it from your input). Text from HTML widgets (`hermes.send()`), buttons whose label differs from their text, and forms whose id or field names carry hidden text first open the confirmation sheet with the full text.
- **Approval commands show every character:** bidi controls, zero-width and other invisible or control characters in a command are shown as `\u202E`-style escapes (also in the approval push and banner), and a command with such or other non-ASCII characters carries the warning "Command contains unusual characters". The risk estimate looks through hidden characters.
- **Bounded streams and transcripts:** the SSE reader drops a single line or frame over 1 MiB instead of buffering it; one answer keeps at most about 1 MB of text and 200 KB of reasoning while streaming, and at most 256 KB of text per message is stored on the device. Shortened answers end with `[…]` and show a notice, so one huge answer can no longer wedge the app or evict the rest of a chat from storage.
- **Shortened history is marked:** when a chat's stored transcript was cut to the newest 300 messages / 1.5 MB, the top of the chat says "Older messages are not stored on this device" instead of silently starting mid-conversation.
- **Connection profiles are never silently lost:** an unreadable stored profile list is kept as a copy on the device instead of being replaced by an empty one, and a list written by a newer app version (or one that could not be read) is read-only until you allow overwriting it in Settings → Connections.

### Known limitations

- iOS is available as a web app (PWA) only; the native app is prepared for TestFlight / App Store, but nothing is submitted yet.
- The macOS and Linux desktop builds are not attached to the GitHub release in this alpha. The macOS app is Apple Silicon only. The Linux AppImage / .deb is an alpha (x86_64, unsigned, no auto-update, glibc 2.35 or newer).
- No app-store builds (Google Play, App Store) yet; the Android APK comes from GitHub Releases.
- No remote push on Android yet: the APK has no Firebase (FCM) setup. While an answer runs, the app's keep-alive service shows a notification; a notification while the app is closed (for example "approval needed") is not available on Android in 0.1. Planned: UnifiedPush / ntfy. Web Push for the web app works, including the iPhone/iPad home-screen app (iOS 16.4+), and needs the bridge. The macOS app shows native notifications (with approval buttons) while it is running.
- The Android APK is built for 64-bit ARM only.
- Schnellfrage (⚡) is experimental and needs the `hermes-ui-plus` Hermes plugin, which calls Hermes' internal `call_llm` and may need an update after a Hermes release. The plugin serves the whole gateway with one quick model, not one per Hermes profile, so ⚡ is not offered in bot (profile) chats.
- Slash commands are handled by the app; Hermes' API server does not interpret them, so unknown ones are sent as plain text.
- `/skills` needs a Hermes version where `/v1/skills` works: unpatched Hermes 0.21.5 to 0.22.0 answer HTTP 500 (upstream issue #120831, fix in PR #124861). The app then says so and that your skills still work.
- Claude answers arrive in one piece on unpatched Hermes: Hermes does not stream providers that run as an external process, such as the Claude subscription plugin (upstream PR #124566; the plugin must opt in as well). The answer appears all at once; the app has no workaround.
- In Hermes "smart" approval mode, Hermes auto-approves most commands, so approval cards appear only when Hermes actually asks.
