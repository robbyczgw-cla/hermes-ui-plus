# Changelog

All notable changes are documented here. The format follows [Keep a Changelog](https://keepachangelog.com), and the project aims to follow [Semantic Versioning](https://semver.org).

## 0.2.2 - 2026-10-25

A patch release with two fixes: the desktop app pairs with a bridge set up by the default wizard, and HUI+ works with Hermes Agent v0.22.3 and newer. Tested with Hermes v0.22.2 and v0.22.5. Most of the fixes are in the bridge, so update it (`npx hermes-ui-plus-bridge@latest setup`, or your install method) and the optional hermes-ui-plus plugin (now 0.2.1: re-run `python3 hermes-plugin/install.py --hermes-home <home> --copy`, then restart the Hermes gateway). Apps still on 0.2.1 get the bridge fixes too.

### Fixed

- **The desktop app pairs with the default bridge setup:** the desktop app talks to the bridge from its own origin (`tauri://localhost` on macOS and Linux, `http://tauri.localhost` on Windows). The setup wizard never allowed that origin, so the bridge answered the browser's CORS preflight with 401 and pairing (and every later call) failed with a network error unless you had added `BRIDGE_CORS_ORIGINS` by hand. The bridge now allows the two desktop origins by default whenever it has a token, for every route (chat, pairing, uploads, media, voice, images, bots, routines, library, quick answers, push, devices); a preflight is answered before the token check, every real request still needs the device token or the one-time pair code, and no cookies or `Access-Control-Allow-Credentials` are involved. A foreign origin still gets no CORS headers. In open mode (`BRIDGE_ALLOW_NO_AUTH`, no token) nothing changes: only origins listed in `BRIDGE_CORS_ORIGINS` count. `BRIDGE_DESKTOP_ORIGINS=off` opts out. The setup wizard shows the allowed browser origins, the bridge's startup summary has an `origins` line, and the new `hermes-ui-plus-bridge doctor` prints the startup checks and features without starting the bridge. Without Tailscale or a public address the wizard no longer calls its `http://127.0.0.1` link a desktop app link: the desktop app connects to `https://` addresses only.
- **Works with Hermes v0.22.3 and newer (current v0.22.5) and still with v0.22.2:** Hermes v0.22.3 brought the "unified gateway", which changed several things the app relies on. Every fix below detects what the server does and keeps the old behaviour on v0.22.2.
  - **Skills library:** the hermes-ui-plus plugin read Hermes' skill list through helpers that v0.22.3 renamed, so the Skills & memory screen stayed empty. It now uses the new names and falls back to the old ones (plugin 0.2.1).
  - **Approvals:** v0.22.3+ only accepts an answer that names the turn's `execution_generation`, so "Allow" / "Deny" from the app failed with `invalid_params` and the turn waited until the approval timed out. The bridge adds the generation from the approval request it saw (or from the run status) and sends exactly what Hermes expects. After a lost stream, the run status now has the pending approval again (v0.22.3+ reports it only as `pending_controls`).
  - **Stop:** on v0.22.3+ a closed connection no longer ends a turn, so Stop had no effect: the command kept running and the next message waited behind it. The bridge now stops the turn through Hermes' run API (`POST /v1/runs/{id}/stop`, now on the bridge's allow-list together with `resolve-unknown`), lets Hermes send its own end of the turn and only then closes the connection; on v0.22.2 the connection close stops it as before.
  - **Every way a turn ends shows something:** v0.22.3+ ends a stopped turn with `cancelled` (shown as "Stopped", partial text kept, never an error), an exhausted step budget with `length` ("Hermes stopped: step limit reached for this answer."), and refuses some turns inside the stream with only a reason code and no text (the bubble stayed empty). Those reasons now read as plain sentences with Retry, for example a chat Hermes paused after a restart cut an answer off ("Continue in new chat" copies the chat up to the last good answer), a chat that belongs to another surface, or Hermes restarting. An answer that ends without any text says so, and an answer Hermes no longer knows after a restart stops loading with a clear line instead of waiting. Approvals use Hermes' own deadline (`timeout_s`) and pass `execution_generation` through when the server sends it.
  - **Bot chats:** v0.22.3+ owns a bot's "Bot Chat" itself and refuses messages into it from the app (`permission_denied`); before, your message simply got no answer. Reminders and routine results still arrive there. On such a Hermes the app now shows the Bot Chat read-only, with a short note and "New chat with <bot>" in place of the input field; the start-screen suggestions open that new chat too. On v0.22.2 the Bot Chat works as before.
- **Bridges older than 0.2.2 and the desktop app:** if you cannot update the bridge yet, add `BRIDGE_CORS_ORIGINS=tauri://localhost,http://tauri.localhost` to its env file and restart it (docs/SELF-HOSTING.md, troubleshooting).

## 0.2.1 - 2026-10-21

### Fixed

- **Plugin installer now updates an existing copy:** `hermes-plugin/install.py --copy` used to print "plugin path exists, leaving it" and exit 0 when an older copy was installed, so after an upgrade the plugin stayed at 0.1.x and the library and bot features stayed unavailable. It now compares manifest version and contents, replaces an older or changed copy (the old one is kept under `<hermes-home>/hermes-ui-plus/backup-<version>`) and says `updated plugin 0.1.1 → 0.2.0`; the same version is a no-op, a newer installed version is kept unless `--force`, and a symlinked install is left alone with a hint. It still never edits `config.yaml` or `plugins.enabled`. Restart the Hermes gateway afterwards.
- **A reminder deleted in the chat no longer rings on the phone:** writing "Delete this reminder" (instead of tapping Delete on the card) deleted the Hermes job, but the device copy from "Also remind me on this device" stayed scheduled and the card still said "This device reminds you too". Now every successful change of the job by Hermes' scheduling tool in a chat takes the copy along: deleted or paused removes it, a new time or name moves it, a job that now repeats removes it (a copy mirrors one run). The card says what happened ("This reminder was deleted in Hermes – removed from this device too", "paused", "moved to …") and drops Change / Delete for a deleted job; after a resume it offers the device copy again. When the app starts, returns to the foreground or opens the chat, it also checks its device copies against the bot's job list, so a reminder deleted, paused or moved elsewhere (another chat, Telegram, the Hermes dashboard) follows too. When that list cannot be read (offline, routines off for this device or bot, older Hermes), nothing is changed. Failed or cancelled tool calls never cancel anything.
- **Nothing the model wrote into a card goes missing:** a gallery's heading, the actual question under a choice's title, a workout's session note (rounds and breaks, equipment, place) and the details of rows in the readable fallback list were dropped silently; they show now. A vocabulary card whose target language the model did not name no longer reads "EN → UND".
- **No raw JSON when a model forgets the code fence:** a card written as a bare `{"type":"suggestions",…}` line (sometimes after a stray `_suggestions` line) showed as text. A complete line like that, standing on its own, is now drawn as the card; while the answer streams it never flashes as text.
- **Sync error messages in the app's language:** when syncing chats with Hermes, loading older chats, renaming or deleting a chat on the server or opening a chat from another device failed, the banner was German even in an English or Spanish app.
- **Live lists follow typed list blocks:** when Hermes wrote each new version of a list as a ` ```checklist `, ` ```agenda ` or ` ```products ` block instead of a ` ```hui ` block, the chat showed the new list, but the live card made from the first one stayed as it was and every answer said "was not changed". Those blocks now update the card.
- **Hermes' changes to a list apply when it guesses the item ids:** a list whose first version came without item ids got a change from Hermes that named items by ids it made up from their names (`"del":"iphone16"`); every change missed and the receipt said "Not applied". An unknown id now means the one item whose name matches it; no match or several matches still change nothing.
- **A removed item stays removed:** after Hermes removed an item, a later full version of the list that copied the old one brought it back as a new item. It now comes back only when your message or the answer's text names it; otherwise it stays out and the receipt says "Not put back, it was removed before".
- **An item opened again no longer looks ticked:** in the receipt under an answer and in a live card's history, an item that was opened again showed the same ✓ as a ticked one; it shows ○ now.
- **Trip days show the right weekday:** when a model paired a date with the wrong weekday ("Friday 24" in a month where the 24th is a Saturday), the day tab showed it as written. A day with an explicit date now takes its weekday from the date.
- **"About <bot>" fits on the screen:** with a few routines, a small phone or large text the sheet grew past the top edge, so the bot's name and model could not be reached. It is capped at 88 % of the screen and its content scrolls.
- **Demo approvals:** answering an approval in the offline demo recorded "run ended" in the receipt instead of the choice you made.

## 0.2.0 - 2026-10-20

### Added

- **Bots as contacts:** when your Hermes connection has profiles besides the default, the drawer gets a "Chats | Bots" switch. The Bots tab lists "Hermes · Default" first, then pinned bots (from Hermes Desktop), then by activity, with avatar, last line, "working ..." and badges for "Approval" and unread. Each bot has exactly one chat, its "Bot Chat" session (the same one Hermes Desktop uses), which never shows up under Chats and is never renamed, deleted or forked, not even by "Delete all chats". "About <Name>" (bot header or chat menu) shows the bot's description and routines. Without profiles the app looks as before.
- **Approvals with the bot's name:** "Research wants to run something", "Reason given by Research", "Allow once / Always allow (only for Research) / Deny". Instead of a countdown it says "Research has been waiting for you since 7:12" and counts down only in the last minute. "Always" is written only to that bot's own config; for the default bot it stays the global list under "More options". "Waiting for you" on the Bots tab opens the chat with the card, and an approval push names the bot ("Research is waiting for your approval").
- **Reminders arrive in the bot's chat:** reminders and routines set from a chat are delivered into that bot's Bot Chat (`deliver: "bot-chat"`, skill 0.7.1), also for the default bot without extra profiles: its thread then appears as a "Hermes" row in the chat list. The job's text shows directly under a quiet marker with the job's name and time, and the bridge sends one push per run with the bot and the job in the title; silent runs notify nobody, and the job's own session or the routines inbox do not ping a second time.
- **Bridge: Bot Chat route and checks:** `POST /api/sessions` only for the exact title "Bot Chat" (returns the existing one, so two devices share one thread). `hermes-ui-plus-bridge doctor bots` reads and checks the multiplex switch, each profile's key, `BRIDGE_PROFILES` and which venv the gateway loaded, and writes no token. `bots backup` also saves `installs/*/facts.json`; `bots rollback` shows its plan first and acts only with `--yes`. The bridge watches every bot's Bot Chat for delivered jobs. Runbook: `docs/BOTS-SERVER.md`.
- **Create a bot (needs the hermes-ui-plus plugin 0.2.0 and an owner who switches it on):** "New bot" on the Bots tab. First pick a role: research, deals & prices, travel planning, daily briefing, code or your own role. You can also start an empty agent and rename it. Then fill in three fields (name, main job, how it should work) and switches for what it may do (search the web, remember things, check in regularly; commands only for the code role, risky ones only after your approval). There is no model picker: a new bot uses the server's default model. Phones get two full-screen steps; tablets and the web get one dialog. The new bot's chat opens with "<Name> is ready" and three starters for its role. While only Hermes exists, the Bots tab shows a "Your own bots" box, or says who decides and, on the owner's device, the command to switch it on. On the server the plugin creates a profile as a clone of the default, without restarting the gateway:
  - its own empty memory and a `SOUL.md` built from the three fields;
  - toolsets from the switches, manual approvals with an empty "always allow" list;
  - the bridge's key as `API_SERVER_KEY` (the key never passes through the app);
  - Hermes Desktop's bot metadata, so Desktop shows the same bot.

  At most 50 bots. Creating is off until the owner runs `hermes-ui-plus-bridge bots enable` (or sets `BRIDGE_BOTS_CREATE=on`). The admin token may create then; a paired device only after `bots grant <device-id>`. Bridge: `GET/POST /bridge/bots`, `GET/PATCH /bridge/bots/<name>`, `GET/PUT /bridge/bots/rights`. A bridge that cannot read the Hermes home lists bots through the plugin. Owner steps: `docs/BOTS-SERVER.md` "Creating bots from the app".
- **Skills & memory** (Settings → Connections, and `/skills` / new `/memory` in the composer): the skills of the chat's bot, searchable and grouped by category, with a detail page. With the hermes-ui-plus plugin (0.2.0) the page also shows whether a skill is off, where it comes from (bundled, Skills Hub, external folder, local) and its instructions (SKILL.md) rendered as Markdown; without it, what Hermes' API offers (name, description, category) and a clear note on Hermes' `/v1/skills` bug in 0.21.5 to 0.22.2. The memory tab shows Hermes' notes (MEMORY.md) and what it knows about you (USER.md) with fill level and last change when the plugin owner shares them (`library.expose_memory`, off by default); otherwise it explains why not. Changes always go through Hermes as a normal chat message ("What do you know about me?", "Ask to forget"); the app never writes memory, skills or config. Bridge: read-only `GET /bridge/library/{config,skills,skills/content,memory}` for the plugin's own bot only (`BRIDGE_LIBRARY=off`). Details: docs/SKILLS-MEMORY.md.
- **Live cards:** a shopping, packing or to-do list, a multi-day trip plan or a product watchlist that Hermes keeps up to date over many turns instead of sending new lists. The card is pinned at the top of the chat (progress ring, "1 change waiting"), opens with its version, what changed and who changed it, and keeps a history with "Back to vN". Your own ticks, additions and deletions go to Hermes with your next message; small updates from Hermes arrive as patches, and every device folds the same chat history to the same state. "Continue as a live card" turns an ordinary list into one. Needs the `hermes-ui` skill 0.7.1; older apps keep seeing ordinary lists. The bridge router points edit requests at the one matching open card.
- **Reminders from the chat, delivered somewhere you see them:** when Hermes sets a reminder with its own scheduling tool (`cronjob_manage`), the reminder card now says where Hermes will post it (no channel, the Bot Chat, every connected channel, or Telegram and the like). On Android and iOS a one-shot reminder also offers "Also remind me on this device": a local notification at the same time, tied to that Hermes job, so the card still knows it after a restart, a moved reminder moves it and Delete removes it. A job created from the app has no channel by default (an API chat cannot receive it), so without this nothing would ring.
- **Routines (optional, on by default; Settings → Chat → Routines turns them off on this device):** "About <Name>" in the chat menu of every Hermes chat (and the bot's header) lists the scheduled jobs Hermes already has for that bot, and "All routines and results" opens the Routines page: grouped into Needs attention, Active, Paused and Completed, the schedule in plain language ("Monday to Friday at 7:00 AM") on the bot's clock, next and last run with the outcome, pause and resume, "Run now" after a confirmation (a full, possibly paid bot run; on a paused job "Resume and run"), a detail page (task, delivery such as "Into the bot's chat", model, the last report on request) and the results inbox. Without the Hermes Agent v0.22 job API, or while the bridge has not enabled routines for that bot (no bot is enabled until the owner runs `routines enable <bot>`), the page explains why and what to do. Creating and editing routines comes later. The offline demo has sample routines. With the switch off there is no routines part in "About <Name>", no results inbox, no routine notifications and no demo routines; a link to the Routines page explains the switch and offers to turn it back on. Reminders from the chat are not affected.
- **Routines (bridge):** the UI-Bridge offers Hermes' scheduled jobs to the app: list and details (`GET /api/jobs`, `GET /api/jobs/{id}`), pause, resume and run now. Creating, editing and deleting jobs and one-off prompt overrides are not possible through the bridge. A run of a paused job needs an explicit "resume" confirmation, finished jobs cannot run, a job can run at most once per 30 s. The bridge sends only a reduced job record (no chat ids, scripts, working directories or provider URLs). `BRIDGE_ROUTINES` is `control` by default; `read` allows viewing only, `off` hides routines.
- **Routines rights (bridge):** routines are opt-in per bot (`BRIDGE_ROUTINES_BOTS`, or `hermes-ui-plus-bridge routines enable <bot>`). The admin token manages them; paired devices may only view unless the owner grants `manage` per device and bot (`routines grant`, or `GET/PUT /bridge/routines/rights` with the admin token). `BRIDGE_ROUTINES` stays the server-wide ceiling. Job responses carry the effective right (`hui.rights`).
- **Routine results inbox (bridge):** the bridge watches the enabled bots for finished runs and keeps each result (final answer, status, error) in its own inbox (`/bridge/routines/inbox`, unread state shared by all devices, 30 days / 300 entries by default). New results are announced as a live `hui.routine` event and as a push to devices that asked for `routines` (title and text only with `BRIDGE_PUSH_PREVIEW=1`); silent runs are stored as read and never pushed. `GET /bridge/routines/capabilities` tells the app what the bridge offers. A device with Routines turned off in the app does not ask for `routines` and gets none of these pushes.

- **"New in this version":** after an update, one calm sheet lists what is new in three rows (live cards, skills, memory). Each row opens the feature: live cards open a new chat with an example request in the composer (not sent), skills and memory open their tab. It shows once per app version, never on a fresh install and never over onboarding or the consent sheet. The list is one place in the code (`WHATS_NEW`).
- **Offline demo, 0.2 edition:** "Keep a shopping list for Saturday's barbecue" makes a live card pinned at the top; the chip "Add charcoal and halloumi, we already have tomatoes" changes it with a patch and shows the change receipt, and your own ticks go along with the next message. The questions of the Skills & memory screen ("What do you remember about me?", "Forget that I dislike coriander", "Which skills do you have?") get real answers with the same data as the screen, also with typos, in English, German and Spanish. When you ask it to forget something, the demo says it stores nothing. The demo memory follows the app language.
- **Offline demo: bot mode:** the demo now has the "Chats | Bots" switch. The Bots tab lists "Hermes · Default" and three invented example bots: Scout (deals & prices) with a delivered price check and an approval waiting for you ("Scout wants to run something", shown under "Waiting for you"), Atlas (travel) with a delivered reminder, and Lumi (daily briefing) with the morning briefing in its chat. "About <Name>" shows each bot's own (invented) routines. "New bot" works with the same roles and fields; the bot stays on this device and answers in its role with sample texts. Anything that needs a real Hermes (routines running in the background, memory, running commands) is said so in the demo's own words, in English, German and Spanish.
- **Skills & memory is easier to find:** a "Skills & memory" row in the drawer (Settings → Connections keeps its row), and the "remembered" note under an answer now opens the Memory tab of that chat's bot.

### Changed

- **"Ask Hermes" opens a new chat:** from Skills & memory (list, skill page, memory) and the Routines "off" screen, the question now starts a new chat with the screen's bot instead of landing in whatever chat was open. An empty draft is reused, so repeated asks do not pile up empty chats.

- **Bots live in the Bots tab, not in the model menu:** the model menu no longer has a "Bot" section; a new chat always starts with the default bot, and the other bots are reached through their own chat in the Bots tab.
- `/skills` opens the Skills & memory screen instead of a sheet.
- **Skill, reminders:** reminders and repeating tasks only go through a scheduling tool; Hermes confirms them only after the tool succeeded and says in one line when the chat will get no message. Without such a tool it says so once, with no reminder button or stand-in card (the `reminder` action stays for other uses).

### Fixed

- **Answers no longer vanish or leave a gap:** an image or gallery block whose photos cannot be found keeps a calm placeholder tile per item and one line with the reason (image search not set up, Wikipedia only, images off, could not load, nothing found) and a link to the setting. A block whose entries were all lost shows a quiet line instead of nothing, and a block type the app does not know (such as `remind`) shows its content readably with a note that nothing was set up. The shapes small models write from memory are understood: choices as `items`, workouts with phases, text durations and rounds, agendas as `items`/`time`, recipe steps with `title` and `detail` and their times, vocabulary as `word`/`language`, quizzes as `items`/`question`, translations as `{language, original, translated}`, and maps without coordinates become a list of places. A readable fallback never shows a quiz solution. (Real-user runs against the default bridge.)
- **Timers:** a newer timer with the same id takes over the running one; one with the same label offers "Start this one instead" instead of running twice.
- **Watchlists, calculator, agenda:** a target price ("Target: 450 €") stays a target and is never shown as the current price; spreadsheet formulas (`IF`, `MAX`, `ROUND`) and `IF(..., "A", "B")` text results are computed; an agenda block with a duration but no end uses that duration instead of a default hour; Hermes' English session-lock lines read in the app language.
- **A ticked live-card item stays ticked** when Hermes sends an update that leaves it out.
- **Router:** one swapped or missing letter in a list word ("lsit", "Einkaufslsite") still counts as a list request, a correctly spelt list word is never "repaired" into another one, and dictated handheld names count as product models in comparisons.
- **Tool-call markup stays out of everything:** besides the answer, raw tool-call markup no longer reaches the screen reader announcement, read-aloud, notifications, the chat preview, search, export or the desktop copy.
- **Consent wording:** the data-sharing consent now also says that your Hermes server keeps the conversations; existing users are not asked again because of 0.2.
- **Short suggestion chips are no longer cut on Android:** "What can you do?" under a demo answer showed as "What can you". Android gave the chip text about 0.1 dp less than its own one-line width, so the last word wrapped into a line the chip had no room for. A short chip now notices that and takes its one-line width at the same font size. German and Spanish were not affected.
- **Live cards stay in step with the chat:** Hermes often answered an edit to a pinned card with an ordinary checklist under its own id instead of a live block, so the card stayed at "Milk". The app now takes an ordinary list that clearly continues the pinned card (same id, alias or title, or at least half of its items) as the next version. What it cannot take is said out loud: a note with "Add to the live card", "... was not changed" under an answer without a block, "not applied" for a patch on unknown items. "Continue as a live card" keeps Hermes' own id and title (the card used to be called "Liste").
- **Live blocks in the shapes models write:** `{"type":"live",...}` wrappers, a trip plan by days and a film watchlist now open as real live cards instead of "cannot be shown". The skill (0.7.x) says plainly that a live card is the node plus `"live":true` under the card's id.
- **Markdown task lists are checklists:** "shopping list to tick off" that Hermes wrote as `- [ ] item` lines now becomes a real checklist (tick, send, continue as a live card). If the skill reference fails to load, Hermes goes on with the core rules and no longer tells you "template not available".
- **No invented sources:** the skill no longer lets Hermes label an answer with a source it did not read.
- **Quiz without the solution:** a choice whose descriptions say "Correct!" or "Wrong" becomes a quiz that explains after you tap.
- **Multi-day plans:** an agenda with "FRIDAY: ... / SATURDAY: ..." or repeated blocks is split into day tabs; tabs written as `items/title/blocks` are recognised and the card shows its places.
- **Counts:** a checklist item with its own comma ("Parmesan, grated") counted twice in the message sent to Hermes ("1 of 12" for a list of 11). It now counts once, and so does a decimal comma.
- **Calculator:** `.toFixed()`, `Math.*` and text ternaries in a formula are computed; a formula that cannot be computed says "cannot be computed" instead of three dashes.
- **Place photos:** a generic place name ("Old town (centre)") gets a photo only together with its city, otherwise a calm category tile; a Wikipedia hit must contain what is specific in the request. (A Salzburg "Altstadt" showed a photo from Warsaw.)
- **Demo live card:** it no longer says "On all devices · through Hermes" offline, but "Kept in this chat · demo".
- **"New in this version" on first start:** the decision is made at app start, so a fresh install without an open chat is not mistaken for an update.
- **Reminders in the phone's time zone:** "remind me tomorrow at 9" meant 9:00 on the Hermes server's clock. Hermes turns now carry a short line with the phone's time zone, UTC offset and date (`[hermes-ui-app] User time zone: …`, changes once a day, so prompt caching stays intact), and the skill makes one-shot reminders an ISO time with that offset; repeating jobs are shifted into the server's zone (Hermes has no per-job time zone, so in the week between the European and US clock changes they run an hour off).
- **Reminder card:** a one-shot reminder that Hermes v0.22 reports as `once at …` / `once in …` was treated as repeating and showed that English schedule text under the card.
- **"Photos?" without web image search:** a bridge without an image search key (no Serper/Brave) now tells the model so with one constant line at the end of its bootstrap message, `[hermes-ui-caps] image_search=off` (also in `/bridge/status` and the startup summary). The `hermes-ui` skill (0.5.2 and later) then never writes query-only `source:"web"` pictures, which nothing could find there, but uses image URLs its extract tool returned (`{url, caption}` gallery items) or text links. With image search, or without the line (older bridge, direct connection), nothing changes. Needs the new bridge and the updated skill.
- **Tool calls written as text:** an answer that contains raw tool-call markup (`<tool_call>{…}</tool_call>` and similar) from a model whose call nothing ran no longer shows that markup as the answer; one quiet line says the tool call is not available and nothing was run. Code blocks that show such markup on purpose stay as they are.

### Removed

- **Ask several bots** (screen, route, texts, `docs/MULTI-BOT.md`, smoke group). Its parts (job API, rights, inbox, push, result renderer, skills & memory per bot) carry the bots instead. A new chat always starts with the default bot.

## 0.1.3 - 2026-10-18

A result card for web searches done with Web Search Plus (WSP), and a handful of fixes around it.

### Added

- **Web result card:** in "Tools and activity" (and in the compact view) a tap on a web search or page-reading row opens a card that shows what the tool reported, and nothing it did not report. For a search: the query, "How it searched" (provider, whether it was chosen automatically or fixed, how sure the routing was, the kind of query, duration, cache age or "freshly fetched", freshness filter), and the results with favicon, domain, date, excerpt and the number under which the answer cites them. For research: pages read, results and duration. For page reading ("How it read the pages"): the pages and, for pages that failed, the reason. Without WSP (a plain `web_search`) the card shows the query and the results. A call whose output cannot be read keeps the old detail view. Titles and excerpts are shown as plain text, links open only as http(s), and the security notice WSP adds to its output stays hidden.
- **Read from WSP 5.1.2:** the card uses the machine-readable header bits (`results`, `elapsed_ms`, `fallback_from`, and `providers` / `pages` for research), so the result count and duration are the tool's own, and a "Fallback chain" line (for example Serper, Brave, Exa) shows which providers failed before one delivered. Pages that were not tried (`Error: not tried: <reason>`, for example the limit of URLs per call) stay in the list with their reason. Output from WSP 5.0.x and 5.1.1 reads as before; unknown header bits are ignored. English, German and Spanish.
- **The card is there while the answer is still being written:** when a web tool finishes, the app fetches the stored tool lines once (Hermes saves them about half a second after the step), so the row and the card appear while the model is still writing instead of after the turn.
- **Better page excerpts:** read pages start with a title line or a "TL;DR"; the card now shows the first real paragraph, never text of the next page.
- **Offline demo:** a new start chip, "Research jet lag tips for a flight east, with sources." (English, German, Spanish). The answer shows a WSP search with fallback, a page read, cited sources and both cards, with made-up results and no server.

### Changed

- **Technical details are collapsed:** under the web result card, the tool name, status, times, call ID and the input JSON sit behind a closed "Technical details" disclosure (German "Technische Details", Spanish "Detalles técnicos"), so the card reads as search information and sources. Other tools keep their detail sheet as before.

With the bridge, the skill's core text comes inline right after that message on every app turn (cached, about 2k tokens; `BRIDGE_SKILL_INLINE=off` to disable), so models that skip loading the skill (seen with Claude Sonnet) still render components and follow the router hint. See [docs/BRIDGE.md](docs/BRIDGE.md#skill-core-inline).
- **Compare cards:** pros and cons are marked only when the answer says so explicitly (check for a pro, minus for a con); everything else stays a neutral fact.
- **Follow-up suggestions:** the `hermes-ui` skill ends informative answers with up to three follow-up questions, shown as a vertical list. The setting "Follow-up suggestions" turns them off; Hermes is then told to skip them.
- **Events and "what's on" questions** route to place cards with photos.
- **Live-data answers search first:** for product, place and weather questions the router tells Hermes the answer needs live data, and the `hermes-ui` skill no longer lets it answer from memory without searching first.
- **`paths` answer component:** 2-6 ways, variants or architectures ("where do the files live", "how does a request travel") as one card: title, verdict badge (neutral, good, warn, bad), a chain of node pills joined by arrows, one note line. Optionally a single choice that sends your pick back. The router recognises these questions and the `hermes-ui` skill documents the format.
- **`blocks` answer component:** an architecture or setup at a glance: one card with up to three columns (variants or tiers) of labelled boxes, an optional shared base layer and a caption. Columns sit side by side on tablets and desktop and stack on a phone. Display-only; router format and skill reference included.

### Security

- **Image proxy hardening (bridge):** `GET /bridge/img` needs a device token and fetches only public `https` hosts on port 443: every resolved address and every redirect (at most 3) is checked against private, loopback, link-local, CGNAT, unique-local, multicast and reserved ranges, and the connection goes to exactly the checked address (no DNS rebinding). Only JPEG, PNG, WebP, GIF and AVIF (checked by magic bytes, never SVG), at most 8 MB, 5 s connect / 15 s total; no client headers, cookies or referrer go out; rate limited per device; logs show only host, status, size and duration.
- **One-time pair codes (bridge):** pair links and QR codes carry a one-time code (`c=`, 32 random bytes, stored only as a hash) instead of a device token. The app trades it once for its token with `POST /bridge/pair/redeem`; the token is created only then. Codes expire after one hour, a second use or an unknown code gets the same `410` answer, redeem is rate limited, and codes and tokens are never logged. `devices add`, `--pair`, the pairing page and the setup wizard print the new links; they never contain a token.
- **Pairing fails closed (bridge):** without a state directory the bridge refuses to pair instead of putting `BRIDGE_TOKEN` into the link. `BRIDGE_PAIR_ADMIN_TOKEN=1` restores the old, unsafe behaviour.
- **Device list writes are locked (bridge):** the bridge, the CLI and the setup wizard change `devices.json` under an exclusive lock file, so a `devices revoke` can no longer be overwritten by the running bridge. State files are written through unpredictable temp names opened exclusively.
- **Pass-through limits (bridge):** the short Hermes routes time out after 30 s (`BRIDGE_UPSTREAM_TIMEOUT_MS`) and cap request bodies (approval answers 8 KB); `/health` forwards no body; clients must send a complete request within `BRIDGE_REQUEST_TIMEOUT_MS` (5 min, headers 30 s) while long streamed answers stay unlimited. Only an allow-list of request headers reaches Hermes, and `Set-Cookie` from Hermes is dropped.
- **Upload quota (bridge):** the upload folder is capped at `BRIDGE_UPLOAD_QUOTA_MB` (default 500; expired files are deleted first, then 507), with at most 2 uploads per token and 6 in total at once.
- **Bounded SSE observers (bridge):** the bridge's own stream observers skip a single SSE line or event over about 1 MiB and log only its size; the app still receives the stream unchanged.
- **Content-Security-Policy for the web app (bridge):** pages served from `BRIDGE_WEB_DIR` carry a CSP (no plugins, no framing, no `<base>` hijack, forms only to the bridge, no plain-http connections or images). `BRIDGE_WEB_CSP=report-only|off` for troubleshooting.
- **Push senders do not follow redirects (bridge):** Web Push and FCM requests treat a 3xx as a failure.
- **Single-use pair links (app):** the app redeems the one-time code in a pair link (`c=`, `POST /bridge/pair/redeem`) for its own device token and does not keep the code; an expired or already used link shows "Pairing link expired or already used".
- **Model-provided messages are confirmed centrally:** a `send` / `ask` from an answer goes out with one tap only when the tapped chip or button shows exactly that text (or a module composed it from your input). Text from HTML widgets (`hermes.send()`), buttons whose label differs from their text, and forms whose id or field names carry hidden text first open the confirmation sheet with the full text.
- **Approval commands show every character:** bidi controls, zero-width and other invisible or control characters in a command are shown as `\u202E`-style escapes (also in the approval push and banner), and a command with such or other non-ASCII characters carries the warning "Command contains unusual characters". The risk estimate looks through hidden characters.
- **Bounded streams and transcripts:** the SSE reader drops a single line or frame over 1 MiB instead of buffering it; one answer keeps at most about 1 MB of text and 200 KB of reasoning while streaming, and at most 256 KB of text per message is stored on the device. Shortened answers end with `[…]` and show a notice, so one huge answer can no longer wedge the app or evict the rest of a chat from storage.
- **Shortened history is marked:** when a chat's stored transcript was cut to the newest 300 messages / 1.5 MB, the top of the chat says "Older messages are not stored on this device" instead of silently starting mid-conversation.
- **Connection profiles are never silently lost:** an unreadable stored profile list is kept as a copy on the device instead of being replaced by an empty one, and a list written by a newer app version (or one that could not be read) is read-only until you allow overwriting it in Settings → Connections.

### Known limitations

- iOS is available as a web app (PWA) only; the native app is prepared for TestFlight / App Store, but nothing is submitted yet.
- Desktop: the macOS app (DMG on GitHub Releases) is Apple Silicon only. The Linux AppImage / .deb is an alpha (x86_64, unsigned, no auto-update, glibc 2.35 or newer).
- No app-store builds (Google Play, App Store) yet; the Android APK comes from GitHub Releases.
- No remote push on Android yet: the APK has no Firebase (FCM) setup. While an answer runs, the app's keep-alive service shows a notification; a notification while the app is closed (for example "approval needed") is not available on Android in 0.1. Planned: UnifiedPush / ntfy. Web Push for the web app works, including the iPhone/iPad home-screen app (iOS 16.4+), and needs the bridge. The macOS app shows native notifications (with approval buttons) while it is running.
- The Android APK is built for 64-bit ARM only.
- Schnellfrage (⚡) is experimental and needs the `hermes-ui-plus` Hermes plugin, which calls Hermes' internal `call_llm` and may need an update after a Hermes release. The plugin serves the whole gateway with one quick model, not one per Hermes profile, so ⚡ is not offered in bot (profile) chats.
- Slash commands are handled by the app; Hermes' API server does not interpret them, so unknown ones are sent as plain text.
- `/skills` needs a Hermes version where `/v1/skills` works: unpatched Hermes 0.21.5 to 0.22.0 answer HTTP 500 (upstream issue #120831, fix in PR #124861). The app then says so and that your skills still work.
- Claude answers arrive in one piece on unpatched Hermes: Hermes does not stream providers that run as an external process, such as the Claude subscription plugin (upstream PR #124566; the plugin must opt in as well). The answer appears all at once; the app has no workaround.
- In Hermes "smart" approval mode, Hermes auto-approves most commands, so approval cards appear only when Hermes actually asks.
